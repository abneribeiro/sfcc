Projeto ponta a ponta

Este é o tema de síntese. O guia do exame espera que você saiba projetar, descobrir requisitos e construir um site com o B2C Commerce, ou seja, que consiga juntar o que viu nos temas anteriores. A página segue o ciclo de um projeto real (discovery, desenho, setup, construção, qualidade e go-live) e implementa uma feature completa, do metadado ao job, com links para o tema que aprofunda cada peça.

Conceitos e glossário

Discovery
Fase de levantar requisitos de negócio e técnicos e confrontá-los com o que a plataforma e o SFRA já oferecem.
Fit-gap
Para cada requisito: fit (nativo, só configurar), config+ (nativo com dados ou metadados) ou gap (exige código ou integração). Gaps viram histórias técnicas.
Solution design
Documento com a topologia de sites, catálogos e price books, a arquitetura de cartridges, o mapa de integrações (síncronas e assíncronas), o modelo de dados (atributos, custom objects), a estratégia de cache, os ambientes e o pipeline.
Go-live
Lançamento em produção: dados e código replicados, configuração por instância, testes de carga, monitoramento e plano de rollback.

Regra de ouro do fit-gap: configure antes de customizar. Promoções, sorting rules, slots, Page Designer, preferências e jobs padrão resolvem muito sem código. Quando customizar, estenda o SFRA num cartridge próprio e nunca edite o base (tema 06).

Desenho da solução

Cartridges e cartridge path

  • app_custom_acme: a marca (controllers estendidos, templates, SCSS e JS, models). Um por marca, ou por site se as diferenças forem grandes.
  • int_*: uma integração por cartridge (serviços, hooks, jobs), reutilizável entre sites.
  • plugin_*: plugins do SFRA (LINK cartridges ou plugins oficiais) entre o custom e o base.
  • bm_*: extensões do Business Manager.

Modelo de dados

  • Atributo de objeto de sistema quando o dado pertence a uma entidade existente (produto, perfil, pedido).
  • Custom object para entidades próprias: replicável para configuração editada em Staging, não replicável para dados criados no storefront (tema 13).
  • Site preferences custom para chaves de configuração (liga e desliga features, limites) com valor por instância (tema 14).

Integrações, cache e ambientes

  • Integrações: classifique cada uma como síncrona ou assíncrona, com o serviço e o profile correspondentes, e defina o plano B se ela falhar.
  • Cache: política por rota (Home, PLP e PDP cacheadas; carrinho, conta e checkout não) e remote includes para os fragmentos pessoais.
  • Ambientes: uma sandbox por desenvolvedor e uma de integração, depois Development → Staging (dados) → Production. Code versions por release, CI e CD (tema 16, tema 01).

Setup do projeto

  1. Repositório: estrutura com cartridges/, metadata/ e test/; .gitignore com dw.json; Node fixado (tema 16).
  2. Sandbox: SFRA na tag certa, npm install, npm run build, upload e import do site de dados do RefArch para referência (tema 05).
  3. Site do projeto: criado no BM ou via site import (metadata/sites/AcmeBR), com locales, moedas, catálogos e price books atribuídos, e o cartridge path (tema 14).
  4. IDE: dw.json apontando para a sua sandbox e a code version de trabalho, debugger configurado (tema 15).
  5. Pipeline: lint, testes, build e deploy na sandbox de integração a cada merge.

Qualidade antes do lançamento

  • Funcional: fluxos críticos E2E (busca → PDP → carrinho → checkout → pedido), em cada locale e moeda, com promoções e cupons.
  • Teste de carga agendado com a Salesforce, com perfil de tráfego realista e cache aquecido. Meça o hit ratio por controller (≥ 70%).
  • Quota Status limpo em Staging; Deprecated API Usage revisado.
  • Service Status e timeouts revisados para cada integração; fallbacks testados com o serviço desligado ou em mock.
  • Segurança: sem segredos no código; CSRF em todo POST; encoding; rate limit e CAPTCHA em formulários públicos.
  • Acessibilidade e SEO: URLs amigáveis (URL rules), redirects do site antigo, sitemap (CreateSitemap), robots.

Checklist de go-live

  1. Código: code version de release em Staging, replicada para Production (code replication) e ativada. A versão anterior fica disponível para rollback.
  2. Dados: catálogos, preços, estoque, conteúdo, promoções, slots e Page Designer editados em Staging e replicados (data replication por grupos).
  3. Configuração por instância (não replicada): credenciais de serviço, chaves e certificados, preferências com valores de produção, OCAPI/SCAPI clients, aliases e hostnames, eCDN e certificados TLS.
  4. Jobs: agendas de produção (imports, export de pedidos, reindex, limpeza) habilitadas e testadas.
  5. Monitoramento: alertas no Log Center (erros, serviços, quotas), notificações de jobs e dashboards.
  6. Plano de rollback: code version anterior, replicação Undo, feature flags (preferências) para desligar features novas.
  7. Hypercare: logs e Service Status acompanhados de perto nos primeiros dias; ciclo de correções curto.

Anti-padrões e pegadinhas de prova

Customizar antes de configurar: código para algo que promoções, slots ou preferências resolvem.

Um cartridge monolítico com marca e integrações misturadas: impede o reuso entre sites e trava upgrades.

Editar dados em Production que deveriam vir de Staging: a próxima replicação sobrescreve tudo.

Esquecer a configuração por instância (credenciais, preferências): o site funciona em Staging e falha em Production.

  • Discovery → fit-gap: nativo primeiro, gaps em cartridges próprios.
  • Dados editáveis pelo merchant: em Staging, depois replicação. Dados de comprador nascem em Production.
  • Integração sem necessidade de resposta imediata → assíncrona.
  • PDP cacheada + parte pessoal → remote include.

  1. O cliente quer "frete grátis acima de R$ 300 para clientes VIP". O que fazer primeiro?

    1. Um hook de cálculo custom
    2. Configurar uma promoção de frete com qualificador de customer group
    3. Uma integração com o ERP
    4. Um custom object

    b. É fit nativo: configure antes de customizar.

  2. Um formulário com CSRF precisa aparecer numa PDP cacheada por 24 h. Como implementar?

    1. Desligar o cache da PDP
    2. Renderizar o form num remote include sem cache que gera o token
    3. Remover o CSRF
    4. Guardar o token em custom cache
    ver resposta

    b.

  3. Os pedidos de aviso são criados pelos compradores. Qual configuração de custom object?

    1. Replicável, escopo global
    2. Não replicável (no-staging), escopo de site, com retenção
    3. Atributo em Product
    4. Site preference
    ver resposta

    b. Objetos replicáveis são somente leitura no storefront.

  4. Tudo funciona em Staging, mas em Production o pagamento falha com 401. Causa mais provável?

    1. Código diferente
    2. Credencial do serviço não configurada em Production (configuração por instância)
    3. Cache
    4. Índice
    ver resposta

    b. Credenciais, chaves e certificados são configurados em cada instância.

    2. Um int_acme_payment no path dos três sites, à esquerda do base
    3. Copiar o código em cada app_custom_*
    4. Um controller global
