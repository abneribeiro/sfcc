Custom objects e extensão de system objects

O B2C Commerce traz um modelo de dados rico (produtos, clientes, pedidos, preferências), e quase todo dado novo cabe nele como atributo custom de um objeto existente. Quando não cabe, existe o custom object: uma "tabela" definida por metadados, sem mudança de esquema de banco. Este tema ensina a decidir entre as opções (a documentação avisa que custom objects podem afetar a performance e "são tipicamente desnecessários"), a definir tipos e atributos, a ler e gravar pela API dentro das quotas, e a lidar com replicação, retenção e import/export.

Conceitos e glossário

System object
Objeto da plataforma (Product, Profile, CustomerAddress, Order, Category, SitePreferences, OrganizationPreferences…). Muitos aceitam atributos custom.
Atributo custom
Campo novo definido por metadados e acessado em obj.custom.nomeDoAtributo.
Custom object type
Definição de um tipo novo (ID, key attribute, atributos, replicação, escopo). É sempre da organização inteira.
Custom object
Uma instância de um custom object type, identificada pelo valor da chave.
Key attribute
Atributo único que identifica cada instância (string ou inteiro).
Storage scope
Onde as instâncias vivem: por site ou da organização (globais, compartilhadas por todos os sites).
Data replication (staging mode)
Se as instâncias do tipo são replicáveis de Staging para Production (source-to-target) ou não (no-staging). Não pode ser alterado depois que o tipo é criado.
Attribute group
Agrupamento que faz os atributos aparecerem nas telas do BM. Um atributo fora de grupo não aparece.
Externally managed
Flag que avisa ao usuário do BM que o valor vem de um sistema externo e não deve ser editado à mão.

A documentação é direta: criar custom business objects "can significantly impact overall performance, is typically unnecessary. Avoid creating a custom business object if there's another possible solution." Em prova, se um atributo custom num system object resolve, ele é a resposta certa.

Atributos de custom objects não podem ser usados em refinements de busca, e atributos localizáveis em custom objects estão depreciados.

Estendendo system objects com atributos

No BM: Administration > Site Development > System Object Types > (objeto) > Attribute Definitions > New. Defina ID, nome e tipo; depois, em Attribute Grouping, ponha o atributo num grupo para ele aparecer nas telas do BM.

Metadados em XML (versionáveis)

Em projeto, defina atributos por arquivo e importe (Site Import ou b2c job import): assim eles entram no Git e chegam iguais a todas as instâncias.

Definindo custom object types

  1. Administration > Site Development > Custom Object Types > New.
  2. ID do tipo (ex.: BackInStockRequest).
  3. Key Attribute: o nome do atributo-chave (pode ser criado depois, mas antes da primeira instância).
  4. Data Replication: replicável ou não. Irreversível.
  5. Storage Scope: Site ou Organization.
  6. Na aba Attribute Definitions, crie os atributos (UUID, creationDate e lastModified já existem).
  7. Na aba Attribute Grouping, crie um grupo e inclua o key attribute: sem isso, não dá para criar instâncias pelo BM.

Os tipos são criados em Staging e replicados (tarefa Custom Object Types). A documentação avisa: nunca defina tipos direto em Development ou Production, porque a replicação os remove.

Os elementos staging-mode (no-staging / source-to-target), storage-scope (site / organization), retention-days e key-definition vêm do metadata.xsd oficial. A semântica exata da limpeza por retention-days (data de referência, frequência) não está detalhada nos guias consultados; confira na ajuda da sua versão antes de depender dela, ou faça a limpeza num job.

Sintaxe das consultas

  • Atributos de sistema pelo nome (creationDate, lastModified, a chave); custom com custom..
  • Operadores: =, !=, <, >, <=, >=, LIKE (com *), ILIKE, AND, OR, NOT, NULL.
  • Use placeholders {0}, {1}… com argumentos, nunca concatenação de strings.
  • Quotas de consulta: até 6 expressões de atributo, 4 sobre atributos custom, 3 critérios de ordenação.

Replicação, escopo e contexto de escrita

Quota de objetos por instância400.000 (aviso em 240.000)400.000 (aviso em 240.000)

O erro clássico: um tipo replicável usado para dados gerados em Production. A próxima replicação com a tarefa Custom Objects apaga e substitui esses registros pelos de Staging. E, além disso, o storefront nem consegue gravá-los. Dados que nascem em Production precisam ser não replicáveis, e a escolha não pode ser mudada depois de criado o tipo.

Ordem na replicação: o tipo (tarefa Custom Object Types) antes das instâncias. A replicação de custom object types também apaga ou sobrescreve tipos definidos diretamente no destino.

Import, export e limpeza

  • Import/export: job steps ImportCustomObjects e ExportCustomObjects, Site Import & Export (unidade Custom Objects) ou a OCAPI/SCAPI (Data API e Shopper Custom Objects, para tipos expostos). Veja o tema 18.
  • Exclusão em massa pelo BM: Custom Object Editor > Find > Edit All > Delete Custom Objects, que roda como batch process.
  • Limpeza programada: um job que apaga registros antigos (por exemplo, NOTIFIED com mais de 30 dias), com uma transação por objeto ou chunk-oriented.

Caso completo: "avise-me quando chegar"

  1. Metadados: o tipo BackInStockRequest (não replicável, escopo de site), importado via XML.
  2. Storefront: um form simples (tema 12) na PDP de produtos indisponíveis; o controller chama backInStockHelpers.register.
  3. Job de notificação (tema 18) agendado depois do import de inventário: para cada pedido pendente cujo produto voltou a ter estoque, envia o e-mail e marca NOTIFIED.
  4. Job de limpeza semanal.
  5. Monitoramento: Administration > Operations > Quota Status para o volume de objetos.

Anti-padrões e pegadinhas de prova

Custom object para dados que pertencem a um system object (ex.: "ProductExtraInfo" com chave = SKU). Use atributo custom no Product.

Custom object como banco de dados genérico (catálogo paralelo, histórico de navegação, analytics): estoura quotas e não tem índice de busca.

Tipo replicável para dados de Production. É apagado pela replicação e é somente leitura no storefront.

getAllCustomObjects no storefront, sem fechar o iterador.

  • Definição de custom object type: Administration > Site Development > Custom Object Types. Instâncias: Merchant Tools > Custom Objects > Custom Object Editor.
  • O tipo é sempre da organização; as instâncias podem ser de site ou de organização.
  • A flag de replicação não muda depois de criado o tipo.
  • O key attribute precisa estar num attribute group para criar instâncias pelo BM.
  • Configuração de site → site preference custom, não custom object.
  • Quota: 400 mil por categoria (replicáveis e não replicáveis); 10 criações por request de storefront.

Checklist: você precisa saber

  • Escolher entre atributo custom, site e organization preference, content asset, sessão, custom object e sistema externo.
  • Criar atributos custom com o tipo certo, agrupá-los e versioná-los em XML.
  • Definir custom object types: chave, escopo, replicação (irreversível), atributos e grupos.
  • Usar CustomObjectMgr para criar, ler, consultar e remover, com transações e iteradores fechados.
  • Explicar o efeito da replicação e por que tipos replicáveis são read-only no storefront.
  • Conhecer as quotas (400 mil; 10 por request; limites de consulta) e planejar limpeza.
  • Importar e exportar custom objects (XML, job steps).
