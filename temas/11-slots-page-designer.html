Content Slots e Page Designer

Os dois mecanismos que dão ao merchant controle sobre a aparência do site sem deploy. Com content slots, o desenvolvedor marca lugares fixos nos templates e o merchant escolhe o que aparece em cada um, quando e para quem. Com o Page Designer, o desenvolvedor cria tipos de página e de componente reutilizáveis e o merchant monta páginas inteiras arrastando componentes num editor visual. Este tema implementa os dois, do template ao cache.

Conceitos e glossário

Library
Biblioteca de conteúdo: content assets, folders e, no Page Designer, páginas e componentes. Pode ser privada (de um site) ou compartilhada.
Content asset
Bloco de conteúdo editável no BM (HTML, atributos custom), identificado por um ID (aid/cid).
Content slot
Lugar fixo num template, declarado com <isslot>, com um ID e um contexto (global, category ou folder).
Slot configuration
Configuração do merchant para um slot: tipo de conteúdo (produtos, categorias, assets, HTML, recomendações), rendering template, agenda, customer groups, rank, default.
Rendering template
ISML que desenha o conteúdo de uma slot configuration, usando a variável slotcontent.
Page type / component type
Definições do desenvolvedor para o Page Designer: arquivo JSON (meta definition) + script .js com render() (+ ISML).
Region
Área de uma página ou componente onde o merchant solta componentes.
Aspect type
Contrato de página dinâmica (ex.: plp, pdp), que recebe a categoria ou o produto em tempo de execução.
Visual editor
O editor do Page Designer no BM (Merchant Tools > Content > Page Designer).

As abordagens convivem. O próprio SFRA mostra isso: Home-Show renderiza a página homepage do Page Designer, se ela existir e estiver visível; senão, o template home/homePage com slots. Search-Show usa uma página de categoria do Page Designer quando há uma atribuída.

Content assets e folders

O guia de assets do SFRA lembra que o corpo de um asset é markup editado pelo merchant e é impresso com encoding="off" no template components/content/contentAsset.isml. Por isso só usuários confiáveis devem ter permissão de editar conteúdo.

O BM descobre os slots varrendo os templates dos cartridges do path. Um slot de categoria ou folder dentro de um template incluído localmente não aparece na lista. O contorno documentado é declarar o mesmo slot no template de renderização da categoria dentro de <isif condition="${false}">, só para o BM enxergá-lo. Slots sem configuração não renderizam nada e geram uma linha de log.

Slot configurations (BM)

Em Merchant Tools > Online Marketing > Content Slots, o merchant cria, para cada slot, uma ou mais configurações com:

  • Content type: Products (até 20), Categories, Content Assets, HTML ou Recommendations.
  • Rendering template: o ISML que o desenvolvedor criou para aquele tipo de conteúdo.
  • Schedule (datas, dias, horários), customer groups, rank, a flag default, e opcionalmente a associação a uma campanha ou A/B test.

Qual configuração aparece? Pela tabela oficial de troubleshooting: sem default e sem agenda, nada aparece; o default aparece quando nenhuma agendada vale; uma agendada válida vence o default; entre várias válidas, vence o menor rank (qualquer rank vence "sem rank"); empate, vence a editada por último. Uma configuração com customer group Everyone tem precedência menor que configurações com outros grupos. Boa prática: sempre ter uma configuração default.

Rendering templates e slotcontent

Dentro do rendering template existe a variável slotcontent (dw.campaign.SlotContent): slotcontent.content (a coleção de produtos, categorias ou assets), slotcontent.slotID, slotcontent.callout (MarkupText) e slotcontent.custom.

Cache de slots

A plataforma cacheia o HTML de cada slot de 0 a 59 minutos, conforme a próxima ativação ou desativação de configuração agendada: em geral 59 minutos, menos quando uma configuração está prestes a entrar ou sair. Slots com recomendações não são cacheados. Por isso uma mudança de configuração pode demorar alguns minutos para aparecer, além do page cache da página.

Page Designer: arquitetura

O processo típico, segundo a documentação: o diretor de e-commerce e o desenvolvedor definem páginas, componentes e layouts; o desenvolvedor cria os page types e component types reutilizáveis e sobe dois cartridges (um com os tipos e outro com os artefatos de UI: traduções e thumbnails, no path do Business Manager); o merchant monta as páginas no visual editor.

  • ID do tipo = subpastas + nome do arquivo, separados por pontos: experience/components/acme_assets/promoStrip.json → acme_assets.promoStrip. Nomes só com letras, números e underscore; o ID com o prefixo component./page. não pode passar de 256 caracteres.
  • O script tem o mesmo nome do JSON, com .js, na mesma pasta, e exporta render.
  • O render devolve uma string: use dw.util.Template(...).render(model).text, nunca dw.template.ISML (que escreve direto na resposta).
  • No editor (BM), páginas nunca são cacheadas; no storefront, valem as regras de cache do capítulo 9.

Sobre required e default_value: o default é usado na renderização e no preview, mas não aparece pré-selecionado no editor. O editor só bloqueia o salvamento quando o atributo é obrigatório e não tem default.

Page types, regions e layouts

  • max_components limita quantos componentes são renderizados ao mesmo tempo (a region pode guardar mais, com agendas e visibilidades diferentes).
  • component_type_inclusions (lista do que é permitido) ou component_type_exclusions (lista do que é proibido) controlam o que cabe na region. Pelo JSON schema oficial (regiondefinition.json), uma mesma region usa uma das duas, nunca ambas.
  • default_component_constructors já preenche a region quando o merchant cria a página: uma boa prática documentada.
  • Componentes de layout (como os commerce_layouts.* do SFRA) são component types com region_definitions próprias.

Sem o helper do SFRA, a forma "crua" é <isprint value="${PageMgr.renderRegion(pdict.page.getRegion('main'))}" encoding="off"/>. O HTML de envoltório padrão é <div class="experience-region experience-main"> e, para cada componente, <div class="experience-component experience-acme_assets-promoStrip"> (os pontos do ID viram hífens). Para mudar tags e classes, use dw.experience.RegionRenderSettings e ComponentRenderSettings (é o que o setClassName do helper faz).

Páginas dinâmicas: aspects, PLP e PDP

Uma página dinâmica recebe dados em tempo de execução. O desenvolvedor cria um aspect type (em experience/aspects) que declara os atributos necessários e o tipo de objeto a que o merchant pode atribuir a página (category ou product). O page type declara supported_aspect_types. O SFRA traz os aspects plp e pdp e os page types productList e productDetail.

Um atributo de componente com "dynamic_lookup": { "aspect_attribute_alias": "category" } recebe a categoria da página automaticamente (o merchant ainda pode sobrescrevê-la). No controller:

É exatamente o que Search-Show do SFRA faz com searchHelper.getPageDesignerCategoryPage(cgid), zerando o cache da rota quando a página tem regras de visibilidade.

Cache e performance no Page Designer

A renderização acontece dentro de dois remote includes aninhados do sistema:

  1. __SYSTEM__Page-Include calcula a visibility fingerprint (quais componentes estão visíveis para este contexto: agendas, customer groups). Só é cacheado se a página e os componentes não tiverem regras de visibilidade; o TTL fica em Manage Sites > (site) > Cache > Time to Live of Page Designer Fingerprint (padrão de 24h).
  2. __SYSTEM__Page-Render (ou -Serialize, para JSON) roda os scripts render e é cacheado conforme as instruções de cache que a página ou os componentes definem, com a fingerprint como parte da chave.
  • Sem nenhuma instrução de cache no page type e nos componentes, a página não é cacheada. Com várias, vale a menor.
  • Nos scripts de render, use response.setExpires(...) e, se personalizado, response.setVaryBy('price_promotion'). Não use <iscache> em templates renderizados via dw.util.Template.
  • Conteúdo que não pode seguir o cache da página (estoque em tempo real, dado do comprador) vai num remote include dentro do componente.
  • Cabeçalhos ou cookies definidos durante o render não chegam à resposta do controller que chamou renderPage.

Limites e atualizações de tipos

  • A saída de uma página renderizada pelo Page Designer é limitada a 3 MB; acima disso a página fica em branco (o log é interno). Evite componentes que listam categorias enormes.
  • A documentação recomenda manter o aninhamento de componentes em 5 níveis ou menos.
  • Definições de tipos ficam em memória: em sandbox, Development e Staging atualizam em cerca de 5 segundos ou com troca de code version; em Production, só com troca de code version.
  • Cuidado ao mudar meta definitions depois que existem páginas: mudar o type de um atributo cria inconsistência com os dados salvos. Crie um componente novo e deprecie o antigo.

Artefatos de UI e editores customizados

Nomes, descrições e thumbnails que o merchant vê no editor vêm de um cartridge no path do Business Manager:

  • Resource bundles: templates/resources/experience/pages/…, …/components/… e …/componentgroups/<grupo>_<locale>.properties (com name=).
  • Thumbnails: static/default/images/experience/pages/<subpasta>/<id>.png para páginas e static/default/experience/components/<subpasta>/<id>.png para componentes.
  • Custom attribute editors: para um atributo type: "custom", o editor_definition.type aponta para um editor em experience/editors/… (meta JSON + script + JS e CSS de cliente) que roda dentro do visual editor e conversa por eventos (subscribe/emit). Também existem editores "breakout", abertos em modal.

Anti-padrões e pegadinhas de prova

Usar dw.template.ISML.renderTemplate no render de componente. Ele escreve na resposta em vez de devolver string. Use dw.util.Template.

Componente que lê o comprador (nome, carrinho) sem remote include. A página inteira passa a variar por comprador, ou mostra o dado errado.

Slot de categoria declarado só num include local. O BM não o encontra.

Mudar o type de um atributo de um componente já usado. Crie outro tipo e deprecie o antigo.

  • Contextos de <isslot>: global, category, folder; context-object é obrigatório para category e folder.
  • Variável do rendering template: slotcontent.
  • Configuração exibida: agenda válida vence o default; menor rank vence; empate, a editada por último.
  • Page Designer = JSON (meta definition) + JS (render) + ISML; ID = caminho com pontos.
  • Regions: max_components, component_type_inclusions/exclusions, default_component_constructors.
  • Página dinâmica = aspect type + supported_aspect_types + PageMgr.getPage(category, true, 'plp').
  • Tipos novos em Production só valem depois de troca de code version.

Checklist: você precisa saber

  • Escolher entre content asset, slot e Page Designer para um requisito.
  • Declarar <isslot> nos três contextos e escrever rendering templates com slotcontent.
  • Explicar como uma slot configuration é escolhida (default, agenda, rank, edição) e o cache de slots.
  • Criar component types e page types (JSON + JS + ISML), com atributos, regions e defaults.
  • Conhecer os tipos de atributo e o objeto que cada um entrega ao script.
  • Renderizar páginas pelo controller (res.page, PageMgr) e páginas dinâmicas com aspects.
  • Explicar o cache do Page Designer (fingerprint, menor TTL entre os componentes, response.setExpires).
  • Entregar resource bundles e thumbnails num cartridge de BM.
