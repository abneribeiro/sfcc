Instalar o SFRA e o sample site

Do zero até ver a loja de demonstração (RefArch) funcionando na sua sandbox: conseguir acesso aos repositórios privados, baixar o código na versão certa, instalar dependências, compilar JS e SCSS, configurar credenciais, enviar os cartridges, importar os dados de demonstração, montar o cartridge path e verificar. No fim, como baixar o código que já está numa instância.

Conceitos e glossário

storefront-reference-architecture
Repositório privado com app_storefront_base e modules. Sem acesso autorizado, o GitHub responde 404, como se o repositório não existisse.
storefrontdata
Repositório com os dados de demonstração do SFRA: sites RefArch e RefArchGlobal, catálogos, price books, inventário, conteúdo, preferências e metadados.
sgmf-scripts
CLI do SFRA para compilar, lintar e fazer upload. É obrigatória para o build.
Plugins
Repositórios opcionais (plugin_wishlists, plugin_giftregistry, plugin-applepay…), versionados com as mesmas tags do base.
dw.json
Arquivo local com host, credenciais e code version de destino, usado pelas ferramentas de upload. Não vai para o Git.
Access key
Em organizações com login unificado do Account Manager, a "senha" do WebDAV é uma access key gerada no BM (seu usuário > Manage Access Keys), com escopo (WebDAV File Access, OCAPI, etc.) e validade de um ano.
Code version
A pasta no servidor que recebe os cartridges (ex.: version1). Precisa estar ativa para o storefront usá-la.
Site import
Administration > Site Development > Site Import & Export: importa um .zip com a estrutura de site export (catálogos, sites, meta, libraries…).

Pré-requisitos e acesso

Acesso aos repositórios privados

  1. Tenha uma conta no GitHub (pode ser pessoal, sem relação com o Salesforce).
  2. Ative a autenticação em dois fatores (2FA) na conta do GitHub; a Salesforce exige.
  3. Associe a conta à organização pela página de SSO da Salesforce Commerce Cloud no GitHub, autenticando com o seu usuário do Account Manager.
  4. Contas inativas por 90 dias são removidas da organização; para voltar, refaça o SSO.

Ambiente local

  • Node.js: a documentação do SFRA cita a versão 18 como testada. O Node serve só para dependências e build, nunca para executar o storefront.
  • Git, e um editor (VS Code com a extensão B2C, ou Prophet; veja o tema 15).
  • Uma sandbox (On-Demand Sandbox) com usuário de BM. O SFRA não deve ser importado em instâncias do PIG.
  • Uma access key com escopo WebDAV File Access (se a organização usa login unificado), ou um API client com permissão de WebDAV.

A documentação é explícita: "Do not import SFRA data into an instance in your Primary Instance Group (PIG)." O sample site serve para sandboxes de estudo e referência.

Obtendo o código na versão certa

Clone os repositórios lado a lado (como irmãos): as ferramentas de build resolvem caminhos relativos como ../storefront-reference-architecture e não funcionam com repositórios aninhados.

v7.0.0 é só um exemplo de tag. Use git tag em cada repositório e escolha a última versão marcada como release (não pre-release) na aba Releases do GitHub. O ponto da documentação é usar a mesma tag em todos os repositórios.

Dependências e build

O que cada passo faz:

ComandoEntradaSaída
compile:jscartridge/client/default/js/*.js (entry points)cartridge/static/default/js/*.js
compile:scsscartridge/client/default/scss/**/*.scss (exceto _parciais)cartridge/static/default/css/**/*.css
compile:fontsfontes de node_modules (ex.: ícones)static/default/fonts

Cada plugin com JS ou SCSS próprio também é compilado, rodando o build dentro do repositório dele, que tem o seu próprio package.json com paths.base.

Se o build falhar com Cannot find module apontando para base/…, quase sempre é o layout de pastas: o plugin espera o SFRA em ../storefront-reference-architecture.

Enviando o código

Os plugins são enviados do mesmo jeito, de dentro do repositório de cada um. Confirme no BM: Administration > Site Development > Code Deployment → clique na code version → a lista de cartridges precisa conter app_storefront_base, modules e os plugins. Marque a versão como ativa se ainda não estiver.

O cartridge modules precisa ser enviado (para o require('server') funcionar), mas a documentação diz que ele não precisa estar no cartridge path.

Importando o sample site (RefArch)

Os dados de demonstração vêm do repositório storefrontdata, no formato de um site export: catálogos, price books, inventory lists, bibliotecas de conteúdo, meta (system object extensions e custom types) e a pasta sites/ com os sites RefArch e RefArchGlobal (preferências, slots, promoções, URL rules, shipping, payment, taxação).

  1. Gere o .zip pela linha de comando. A documentação avisa que zips feitos com o utilitário de arquivo do macOS causam erro no import.
  2. No BM: Administration > Site Development > Site Import & Export.
  3. Em Import, escolha Local, faça upload do .zip, selecione-o e clique Import.
  4. Acompanhe o status na mesma tela (ou no log do job de import) até Success.

O nome da pasta dentro do storefrontdata varia conforme a versão do repositório (por isso o ls antes). Use a pasta indicada no README da tag que você fez checkout.

Ordem quando há sites próprios

Numa sandbox que também terá o seu site customizado, importe primeiro o SFRA e depois o seu site: se houver conflito de atributos custom, os do seu site sobrescrevem os do SFRA, e os seus dados são preservados. Importar o SFRA por cima de sites customizados pode sobrescrever atributos e perder dados.

Configuração pós-import

1. Cartridge path

Administration > Sites > Manage Sites > RefArch > Settings → campo Cartridges. Repita para RefArchGlobal.

O cartridge path do Business Manager é outro (Manage Sites > Business Manager Site > Settings) e só importa para cartridges de BM (bm_*, tema 07).

2. URLs simples durante o desenvolvimento

Em Merchant Tools > Site Preferences > Storefront URLs, desmarque Enable Storefront URLs no começo do desenvolvimento. Assim você chama qualquer rota direto:

3. Preferências do SFRA

Em Merchant Tools > Site Preferences > Custom Preferences > Storefront Configuration estão os atributos custom criados pelo import: tipo de instância usado pelo SFRA, tag de verificação do Google, e-mails de notificação e o ID do price book de lista padrão, entre outros.

4. Índices de busca e cache

  • Merchant Tools > Search > Search Indexes: reconstrua os índices (produto, conteúdo, sugestões) do site importado.
  • Em sandbox, deixe o page cache desligado (Administration > Sites > Manage Sites > RefArch > Cache) para ver alterações na hora.

5. Proteção por senha (opcional)

Sandboxes ficam expostas na internet. A Storefront Password Protection (preferências de site) pede usuário e senha para o storefront; em organizações com login unificado, a senha pode ser uma access key com escopo Protected Storefront Access.

6. Verificação (smoke test)

  1. Home carrega com header, menu e slots.
  2. Uma categoria mostra produtos (índice ok) e os filtros funcionam.
  3. Uma PDP mostra preço e disponibilidade; selecionar variação atualiza a imagem.
  4. Adicionar ao carrinho, aplicar um cupom de demo, ir ao checkout.
  5. Concluir um pedido de teste com o cartão de demonstração do basic_credit (aceito sem gateway real).
  6. Ver o pedido em Merchant Tools > Ordering > Orders.

Baixando o código de uma instância

"Download its code" também cobre o caminho inverso: trazer para a máquina o que está numa instância, para auditar, comparar ou recuperar uma versão.

Sem CLI, qualquer cliente WebDAV (Cyberduck, WinSCP, a extensão do VS Code) acessa https://<host>/on/demandware.servlet/webdav/Sites/Cartridges/<code-version>/ com o usuário e a access key. Em Code Deployment você também pode baixar uma code version como .zip.

A fonte da verdade do código é o Git, não a instância. Baixar da instância serve para diagnóstico ("o que está rodando de fato em Staging?"), nunca como fluxo normal de trabalho.

Anti-padrões e pegadinhas de prova

Importar o SFRA em Staging ou Production. A documentação proíbe importar os dados do SFRA no PIG.

Misturar tags (base v7 com plugin de v6). Só versões com a mesma tag foram testadas juntas.

Versionar o dw.json com senha ou access key.

Esquecer o build antes do upload. Sem compile:js e compile:scss, o static/ fica sem os bundles e a loja carrega sem estilo ou sem comportamento.

  • "Quais repositórios são obrigatórios?" → storefront-reference-architecture, sgmf-scripts e storefrontdata; o resto é opcional.
  • "Como os repositórios devem ficar no disco?" → lado a lado, não aninhados.
  • "Para que serve o Node no SFRA?" → só dependências e build; o servidor roda o motor de script do B2C.
  • "Onde se importa o sample site?" → Site Import & Export, numa sandbox.
  • "O cartridge modules vai no cartridge path?" → não precisa, mas precisa ser enviado.
  • "Mudança não aparece depois do upload" → code version errada, ou não ativa; confira em Code Deployment.

Checklist: você precisa saber

  • Conseguir acesso aos repositórios privados (2FA + SSO pelo Account Manager).
  • Clonar como irmãos e fixar a mesma tag de release em todos.
  • Rodar npm install e os comandos de compile, e saber o que cada um gera.
  • Escrever um dw.json e saber por que ele fica fora do Git.
  • Enviar código (uploadCartridge ou b2c code deploy) e ativar a code version.
  • Importar os dados de demonstração por Site Import e saber as restrições (nada de PIG; zip pela linha de comando).
  • Configurar o cartridge path dos sites RefArch e RefArchGlobal.
  • Reconstruir índices e verificar a loja ponta a ponta.
  • Baixar o código de uma instância para diagnóstico.

Questões de fixação

  1. Ao tentar clonar storefront-reference-architecture, o GitHub responde 404. O que é mais provável?

    1. O repositório foi apagado
    2. A conta do GitHub não está autenticada na organização Commerce Cloud (SSO, 2FA)
    3. Falta o dw.json
    4. A sandbox está parada
    ver resposta

    b. Repositórios privados respondem 404 a contas sem acesso, como se não existissem.

  2. Qual comando gera os arquivos de static/default/js?

    1. npm run uploadCartridge
    2. npm run compile:js
    3. npm install
    4. npm run lint
    ver resposta

    b. O compile empacota os entry points de client/default/js.

  3. Onde os dados do SFRA podem ser importados?

    1. Em Staging, para replicar a Production
    2. Numa sandbox, por Site Import & Export
    3. Em Production
    4. Em qualquer instância
    ver resposta

    b. A documentação proíbe importar dados do SFRA em instâncias do PIG.

  4. Você quer adicionar o plugin de wishlists à loja RefArch. Qual cartridge path é correto?

    1. app_storefront_base:plugin_wishlists:lib_productlist
    2. plugin_wishlists:lib_productlist:app_storefront_base
    3. modules:plugin_wishlists
    4. lib_productlist:app_storefront_base:plugin_wishlists
    ver resposta

    b. O plugin estende o base, então fica à esquerda dele; lib_productlist é a dependência compartilhada do plugin.

  5. Seu código foi enviado, mas o storefront continua mostrando a versão antiga. O que conferir primeiro?

    1. A política de impostos
    2. Se a code version do dw.json é a ativa em Code Deployment
    3. O price book
    4. A replicação
    ver resposta

    b. Upload numa versão inativa não afeta o storefront. Também vale conferir o cache e o cartridge path.

  6. Por que o dw.json não deve ir para o repositório?

    1. Porque é gerado no build
    2. Porque guarda host e credenciais em texto puro
    3. Porque o Git não aceita JSON
    4. Porque muda a cada compile
    ver resposta

    b. Use .gitignore e, no CI, variáveis de ambiente no cofre de segredos.
