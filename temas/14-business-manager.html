Business Manager para desenvolvedores

O Business Manager (BM) é onde código e configuração se encontram. Um desenvolvedor usa o BM para ativar code versions, criar e configurar sites, definir o cartridge path, criar preferências custom, mover dados entre instâncias (Site Import & Export e os módulos de Import & Export), configurar URLs e locales, e conceder permissões. Este tema é o mapa dessas telas, com os caminhos exatos, o que cada configuração faz e como automatizá-la por XML ou pelo CLI.

Conceitos e glossário

Merchant Tools
Menu por site: catálogo, preços, conteúdo, promoções, busca, pedidos, clientes, site preferences.
Administration
Menu da organização/instância: sites, code deployment, replicação, jobs, global preferences, system e custom object types, usuários e roles, operações.
Global preferences
Configurações da organização (locales ativos, fuso da instância, segurança, sequence numbers, feature switches, retenção). Custom: atributos de OrganizationPreferences.
Site preferences
Configurações de um site (locales e moedas permitidos, storefront URLs, baskets, pedidos, busca, source codes…). Custom: atributos de SitePreferences.
Site Import & Export
Exporta ou importa um .zip com dados globais e de sites (exceto código): ideal para clonar e versionar configuração.
Import & Export (módulos)
Telas por área (catálogo, conteúdo, clientes, promoções…) para importar e exportar XML de um tipo de dado.
Account Manager
O serviço de identidade da Salesforce Commerce Cloud: usuários, API clients e roles de acesso às instâncias (login unificado no BM).

Code versions e compatibility mode

Uma code version é uma pasta de cartridges; a instância usa a ativa. Em Code Deployment você cria versões vazias (Add), ativa (Activate), volta para a anterior (Rollback), renomeia, baixa e apaga versões inativas.

  • Ativar uma versão troca imediatamente o código usado e limpa os caches dependentes.
  • Rollback ativa a versão anterior e o compatibility mode dela, se a pasta ainda existir.
  • A plataforma apaga sozinha as versões mais antigas, preservando a ativa e a anterior. A retenção é configurável de 3 a 20 (padrão 10).
  • Production rejeita upload WebDAV na versão ativa: lá, só se envia para versões inativas. A boa prática é subir sempre para uma versão nova em Staging e replicar.
  • Segurança obrigatória desde 2020: certificado de cliente (2FA) para enviar código a Staging e uploads bloqueados em Production (Global Preferences > Security > Access Restriction). Código chega a Production por code replication.

Compatibility mode

Cada code version tem um compatibility mode (API version), ativado junto com ela. Dá para escolher modos mais novos que o ativo ou voltar para o anterior, nunca um mais antigo que o anterior. Todos os cartridges de uma aplicação usam o mesmo modo. A recomendação é mudar em todas as instâncias, evitar modos diferentes entre Staging e Production e não mudar direto em Production.

Toda mudança em produção vai numa code version nova, mesmo um hotfix. A documentação insiste: subir correção direto na versão ativa impede rollback rápido.

Sites: criação e configuração

Criar um site

  1. Administration > Sites > Manage Sites > New.
  2. ID: até 32 caracteres alfanuméricos, hífen e underscore (sem espaços). Não use o mesmo ID de uma library compartilhada.
  3. Currency: a moeda padrão (o site pode ter outras).
  4. Taxation: Net (EUA, imposto somado) ou Gross (Europa e Ásia, preço com imposto).
  5. Apply: o site nasce vazio, com as abas General, Settings, Cache e Security.

Ligar os dados ao site

  • Catálogo: o storefront catalog do site (Products and Catalogs > Catalogs, no catálogo, Site Assignments).
  • Price books: Price Books > (book) > Site Assignments (só na moeda do site).
  • Inventory list: Inventory > (lista) > Site Assignments (uma por site).
  • Library: a do site, ou uma compartilhada.
  • Locales (capítulo 5) e índices de busca reconstruídos.

Settings, cache e status

AbaO que o dev configura

Para desenvolver numa sandbox: page cache desligado e TTL de estático 0. Nunca faça isso em Development ou Production.

Para acessar o BM por um hostname próprio (ex.: staging.acme.com), adicione-o à hostname allowlist em Manage Sites > Business Manager > Hostnames (até 10). Sem isso, alguns módulos mostram erro.

Locales, moedas e fusos

  1. Organização primeiro: Administration > Global Preferences > Locales ativa os locales da instância (pt_BR, es_AR…), com formatos regionais e a cadeia de fallback (pt_BR → pt → default).
  2. Site depois: Merchant Tools > Site Preferences > Locales escolhe quais locales ativos o site aceita e qual é o padrão.
  3. Moedas: Site Preferences > Currencies; cada moeda precisa de price books próprios.
  4. Fusos: o da instância (Global Preferences > Instance Time Zone, usado em jobs e relatórios) e o do site (usado nas datas do storefront e em <isprint timezone="SITE">).

O fallback de locale configurado no BM vale para atributos localizáveis de objetos persistentes (nome do produto, conteúdo). Ele não vale para templates, forms, resource bundles ou estáticos de cartridges, que usam a pasta do locale ou default.

Criando uma preferência custom

  1. Administration > Site Development > System Object Types > SitePreferences > Attribute Definitions > New.
  2. Em Attribute Grouping, crie um grupo (ele vira uma seção em Custom Preferences) e inclua o atributo.
  3. Defina o valor em Merchant Tools > Site Preferences > Custom Preferences > (grupo).

Os mesmos passos valem para OrganizationPreferences. Preferências custom marcadas como obrigatórias não podem ser gravadas vazias, nem pelo BM nem por import.

Valores diferentes por tipo de instância

O preferences.xml de um site (formato do preferences.xsd oficial) aceita, dentro de <custom-preferences>, os blocos all-instances, development, staging e production. Um único arquivo versionado configura todos os ambientes:

O XSD confirma os quatro blocos. Como a plataforma resolve o valor quando há all-instances e um bloco específico ao mesmo tempo (e como sandboxes se encaixam, já que reportam tipo "development") não está detalhado nos guias consultados. Teste o comportamento antes de depender dele.

Feature switches

Funcionalidades novas que podem quebrar comportamento existente chegam desligadas em Administration > Global Preferences > Feature Switches. A documentação recomenda ligar primeiro em sandboxes, testar, e só então ligar no PIG. Um exemplo que aparece em integrações é o switch que habilita a execução de hooks de OCAPI/SCAPI.

Site Import & Export e os módulos de Import & Export

Site Import & Export

Administration > Site Development > Site Import & Export. Gera ou lê um .zip no formato site.xsd, com dados globais (preferências, custom object types, extensões de system objects, custom preferences, schedules, catálogos, price books) e de sites (custom objects, libraries, customer groups, shipping, tax, payment, inventory, stores, preferências, busca, source codes, atribuições). Código não entra.

UsoComo
Montar uma sandbox igual à de outro devExporte da origem e importe na sandbox (mesmos IDs de site)
Trazer dados de Production para depurarExporte só as unidades necessárias. Desmarque Users e Access Roles (ou sobrescreve usuários e permissões do destino); evite dados de clientes por privacidade
Versionar configuraçãoExports são ordenados (catálogo por SKU, inventário por produto…), então diffs entre exports mostram mudanças reais
  • Local (upload do seu computador) ou Remote (até 50 GB).
  • Save in Global Export Directory: num PIG, o arquivo fica visível para as outras instâncias do PIG; numa sandbox, para as outras sandboxes da SIG.
  • Um export que falha gera um zip com sufixo -invalid.
  • Compatibilidade de formato só é garantida entre instâncias da mesma versão da plataforma.
  • Jobs custom importados numa sandbox não rodam por agendamento (scheduled jobs ficam desativados em sandboxes); rode-os manualmente.

Os modos de import (MERGE, UPDATE, REPLACE, DELETE) e a automação por jobs estão no tema 18. Boas práticas oficiais: feeds delta (só as diferenças) sempre que possível, e arquivar ao menos o último feed, porque imports não têm rollback.

URLs, aliases e redirects

  • Storefront URLs (Site Preferences > Storefront URLs): liga as SEO URLs (/pt-br/tenis-corrida.html em vez de /on/demandware.store/Sites-…/Product-Show). Desligue no começo do desenvolvimento para testar rotas direto.
  • URL rules: como as URLs de catálogo, conteúdo e pipelines são geradas (prefixos, locale no caminho, caracteres).
  • Aliases (SEO & Discoverability > Aliases): o arquivo JSON que mapeia hostnames para sites e locales. É específico de cada instância e não é replicado; configure-o em cada uma.
  • URL redirects e mappings: redirecionamentos de URLs antigas (301) e mapeamentos estáticos e dinâmicos.
  • Enforce HTTPS: global (Global Preferences) ou por site.

Gere URLs sempre com URLUtils (url, https, abs, staticURL). Assim, ligar SEO URLs, mudar URL rules ou trocar de domínio não exige mudança de código nem de conteúdo.

Usuários, roles e permissões

  • Login unificado: desde a 19.5, instâncias novas usam o login do Account Manager. Para ferramentas externas (WebDAV, OCAPI, storefront protegido), cada usuário gera access keys com escopo, que valem um ano.
  • Roles (Administration > Organization > Roles & Permissions): conjuntos de permissões atribuídos a usuários.
  • Business Manager Modules: Read ou Write por módulo, por contexto (organização ou sites). Read-only também vale para chamadas de API do usuário.
  • Functional permissions: ações específicas, como gerenciar price books de site ou executar jobs.
  • WebDAV permissions: leitura e escrita em pastas (/catalogs/*, /libraries/*, /dynamic/*…).
  • Roles com triângulo amarelo são sensíveis (gerenciam usuários ou roles).

Princípio do menor privilégio: devs com escrita em Staging só nos módulos necessários; em Production, normalmente leitura. Separe quem define e quem executa replicações (as best practices de replicação sugerem isso). Novos módulos de BM (cartridges bm_*) precisam de permissão explícita.

Roteiro: preparar um site numa sandbox nova

  1. Code Deployment: crie e ative version1; envie os cartridges.
  2. Importe os metadados do projeto (atributos, CO types, preferências, serviços, jobs) com Site Import ou b2c job import.
  3. Importe ou crie o site (ID, moeda, taxação) e os dados (catálogos, price books, inventário, conteúdo).
  4. Defina o cartridge path do site e o do BM (se houver bm_*).
  5. Locales: ative na organização e depois no site; moedas.
  6. Cache: page cache desligado e TTL de estático 0 (só na sandbox).
  7. Storefront URLs desligadas no início; aliases, se testar hostnames.
  8. Reconstrua os índices de busca.
  9. Configure os serviços (credentials de teste ou mock) e as permissões de OCAPI, se o projeto usar.
  10. Abra o storefront pelo menu Storefront do BM e faça o smoke test.

Anti-padrões e pegadinhas de prova

Hotfix direto na code version ativa de Production. Production nem aceita esse upload; e mesmo em Staging, sem versão nova não há rollback.

Importar um export de Production com Users e Access Roles numa sandbox: sobrescreve usuários e permissões.

Configurar preferências à mão em cada instância sem versionar. Use o XML de preferências (com blocos por instância) no repositório.

  • Cartridge path: Manage Sites > (site) > Settings.
  • Site novo: ID, moeda padrão e taxação (Net ou Gross).
  • Locale: ativar na organização (Global Preferences) antes de permitir no site.
  • Custom preference: atributo em SitePreferences ou OrganizationPreferences via System Object Types, mais um attribute group.
  • Site Import & Export não leva código.
  • Compatibility mode: ativar mais novo ou voltar ao anterior; nunca mais antigo que o anterior.
  • Aliases são por instância e não são replicados.

Checklist: você precisa saber

  • Diferenciar Merchant Tools e Administration e achar as telas de dev.
  • Gerenciar code versions (ativar, rollback, retenção, regras de upload) e compatibility modes.
  • Criar um site (ID, moeda, taxação), ligar dados e configurar cartridge path, cache e status.
  • Configurar locales (organização e depois site), moedas e fusos.
  • Criar e ler preferências custom globais e de site; usar valores por instância no XML.
  • Usar Site Import & Export e os módulos de Import & Export corretamente (sem Users e Roles).
  • Configurar Storefront URLs, aliases e redirects.
  • Gerenciar roles e permissões com menor privilégio.
