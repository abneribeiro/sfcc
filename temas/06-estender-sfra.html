Implementar e estender o SFRA

Implementar um site sobre o SFRA é decidir, requisito a requisito, quanto código escrever. Primeiro: isso se resolve com configuração? Existe plugin ou LINK? Se for preciso código, dá para estender o que existe, ou é necessário substituir? Este tema dá os critérios dessa decisão e as técnicas oficiais de extensão: server.extend com append, prepend e replace; module.superModule; sobrescrita de templates, forms e textos; e o padrão dos plugins.

Conceitos e glossário

Overlay
Um cartridge seu, à esquerda do base no cartridge path, com arquivos de mesmo nome e caminho que "cobrem" os do base.
module.superModule
Dentro de um módulo, aponta para o módulo de mesmo nome e mesmo caminho no próximo cartridge à direita do atual. É a base de toda extensão: controllers, models, helpers, scripts.
server.extend(x)
Copia as rotas do controller x (normalmente module.superModule) para o server atual, para que você possa modificá-las.
append
Acrescenta passos ao fim da cadeia de uma rota existente. A cadeia original roda inteira antes.
prepend
Acrescenta passos ao início da cadeia.
replace
Descarta a cadeia original da rota e registra uma nova.
viewData
O objeto acumulado que vira o pdict do template (ou o JSON). Lido com res.getViewData() e alterado com res.setViewData().
Plugin cartridge
Cartridge que adiciona uma feature inteira por extensão (wishlists, gift registry), sem tocar no base.

Customizar ou usar o que já existe?

O item A6 do exame pede exatamente esta habilidade: entender os componentes do SFRA e da plataforma para decidir quando escrever código. A ordem de preferência:

Critérios para justificar código: (1) a configuração não atende; (2) o código estende em vez de copiar; (3) não degrada performance (cache, quotas); (4) o merchandiser continua autônomo; (5) o upgrade do SFRA continua barato.

prepend: guarda antes da lógica original

Interromper a cadeia emitindo route:Complete é um padrão comum em projetos SFRA (a rota é o this dentro do middleware, e o server escuta esse evento para renderizar). Ele depende de detalhes internos do módulo server. A alternativa mais conservadora é um replace da rota com a validação incluída.

replace: quando o comportamento original não pode rodar

Use quando o original faz algo caro ou com efeito colateral (chamada a serviço externo, escrita em sistema de terceiros) que não deve acontecer. O guia oficial alerta: com append, a cadeia original sempre roda, e uma chamada externa pode acontecer duas vezes.

Rotas novas num controller existente

  • "Adicionar dados à PDP sem duplicar a lógica" → server.extend(module.superModule) + append + getViewData/setViewData.
  • "Evitar uma chamada de serviço duplicada" → replace.
  • "Mudar um passo do meio da cadeia" → não dá para mexer num passo isolado: substitua a rota.
  • "Exigir HTTPS ou login numa rota existente" → a documentação recomenda replace da rota com o middleware desejado.

Helpers e scripts

Para a sobrescrita valer, o base precisa ter feito require('*/cartridge/scripts/helpers/productHelpers') (com *, que segue o cartridge path), e não require('~/cartridge/…') (o próprio cartridge). O SFRA usa */cartridge/… quase sempre, justamente para permitir overlays.

Sobrescrevendo templates

Um template no seu cartridge com o mesmo caminho relativo substitui o do base. Não existe merge: o arquivo inteiro passa a ser o seu. Por isso, sobrescreva o menor template possível. Os templates do SFRA são divididos em componentes justamente para isso.

Os nomes dos componentes de product/components/ variam entre versões do SFRA. Antes de sobrescrever, abra o template da página na sua versão do base, veja quais componentes ele inclui e escolha o menor que resolve.

O guia oficial lista estes anti-padrões: sobrescrever variáveis do pdict, apagar propriedades do pdict e trocar algo do pdict por um valor de assinatura diferente. Outros templates e plugins esperam a estrutura original.

Estáticos

Imagens, fontes e outros arquivos em static/default/… seguem a mesma regra do cartridge path: o primeiro arquivo encontrado com aquele caminho vence. CSS e JS de cliente seguem as regras de build do tema 04.

Instalando um plugin

  1. Clone o repositório do plugin na mesma tag do SFRA.
  2. Rode npm install e o build (se o plugin tiver JS ou SCSS).
  3. Envie o cartridge do plugin (e as dependências dele, como lib_productlist).
  4. Importe os metadados ou dados do plugin, se houver (custom objects, preferências, atributos): o README de cada plugin indica.
  5. Ponha o plugin no cartridge path à esquerda do base e à direita do seu custom.
  6. Se o seu custom estende telas que o plugin também estende, declare o plugin em paths e importe dele (não do base) no JS e no SCSS.

Com dois cartridges estendendo o mesmo controller (custom e plugin), a cadeia de module.superModule se encadeia: o custom estende o plugin, que estende o base. Por isso a ordem no cartridge path define a ordem dos append.

Anti-padrões e pegadinhas de prova

Copiar o controller do base inteiro para o custom. Você congela uma versão antiga e perde as correções. Use extend com append/prepend e só faça replace da rota que precisa.

append numa rota que chama serviço externo para "corrigir" o resultado. O serviço é chamado de novo (ou o resultado dele é descartado). Use replace.

Esquecer server.middleware.get ou post no replace. O replace usa server.use, que não filtra método: a rota passa a aceitar qualquer verbo.

server.append sem server.extend antes. Sem herdar as rotas, a rota "não existe" e o server lança Route with this name does not exist.

Reescrever uma feature que a plataforma oferece (promoções, preços, slots, busca). Mais código, menos autonomia para o negócio, upgrades mais caros.

  • module.superModule → o módulo de mesmo caminho no próximo cartridge à direita.
  • server.extend(module.superModule) é obrigatório antes de append, prepend ou replace.
  • append roda depois da cadeia original; prepend, antes.
  • Sobrescrever um template = arquivo de mesmo caminho em cartridge à esquerda; não há merge.

Checklist: você precisa saber

  • Aplicar a escada de decisão: configuração → plugin/LINK → extensão → replace → código novo.
  • Criar um cartridge de customização com paths e posicioná-lo no cartridge path.
  • Usar server.extend, append, prepend e replace, sabendo o efeito de cada um na cadeia.
  • Saber quando append é perigoso (serviços externos) e quando replace é necessário.
  • Estender models, decorators e helpers com module.superModule.
  • Sobrescrever o menor template possível, sem alterar a estrutura do pdict.
  • Estender forms (arquivo inteiro), textos e estáticos.
  • Instalar e ordenar plugins.

Questões de fixação

  1. Você precisa exibir na PDP um atributo custom do produto. Qual é a abordagem recomendada?

    1. Copiar Product.js do base e editar
    2. server.extend(module.superModule) + server.append('Show', …) acrescentando ao viewData, e um componente de template
    3. Editar app_storefront_base
    4. Criar um pipeline
    ver resposta

    b. Estender preserva o comportamento do base e recebe as correções de upgrade.

  2. A rota Cart-AddProduct chama um serviço de reserva de estoque. Você precisa trocar o serviço. O que usar?

    1. append, chamando o serviço novo
    2. replace
    3. prepend, chamando o serviço novo
    4. Editar o base
    ver resposta

    b. Com append ou prepend, a cadeia original (com o serviço antigo) continuaria rodando. O guia orienta: com serviço externo, substitua a rota.

  3. O que module.superModule referencia dentro de app_custom/cartridge/models/cart.js, com path app_custom:plugin_x:app_storefront_base?

    1. O models/cart.js do próprio app_custom
    2. O models/cart.js do próximo cartridge à direita que tenha esse arquivo (plugin_x, se existir; senão o base)
    3. Sempre o do base
    4. O controller Cart.js
    ver resposta

    b. É o módulo de mesmo caminho no próximo cartridge à direita no path.

  4. Depois de server.replace('Show', function (req, res, next) {…}), a rota passou a aceitar POST. Por quê?

    1. Bug da plataforma
    2. replace registra via server.use, sem o filtro de método; é preciso passar server.middleware.get
    3. Faltou server.exports()
    4. O cache estava ligado
    ver resposta

    b. No server.js, só get() e post() inserem o filtro; replace() chama use().

  5. Qual destes é anti-padrão segundo o guia do SFRA?

    1. Acrescentar uma propriedade nova ao viewData
    2. Trocar pdict.product por um objeto de estrutura diferente
    3. Criar um decorator novo
    4. Usar assets.addCss
    ver resposta

    b. Não sobrescreva, não apague e não mude a assinatura de variáveis do pdict.

  6. O negócio quer "frete grátis acima de R$ 300 para clientes cadastrados". Qual é a melhor solução?

    1. Hook de frete customizado
    2. Promoção de shipping com qualifier de customer group Registered
    3. append no checkout
    4. Atributo custom no basket
    ver resposta

    b. É configuração pura; código só se a regra fosse impossível de modelar como promoção.
