OCAPI e SCAPI: as APIs REST do B2C Commerce

O exame cobra a OCAPI (Open Commerce API): recursos, URLs, métodos, permissões e, sobretudo, hooks para customizar a lógica de negócio. A plataforma, porém, já mudou: a OCAPI foi marcada como deprecated em abril de 2026, e o caminho para projetos novos é a SCAPI (B2C Commerce API) com o SLAS. A boa notícia é que os hooks são os mesmos (dw.ocapi.shop.*) nas duas APIs. Este tema cobre a OCAPI como a prova pede e mostra o equivalente em SCAPI.

Conceitos e glossário

OCAPI
API REST que roda no servidor de aplicação da instância. Tem três partes: Shop API (comprador ou agente comprando por ele: produtos, busca, cesta, pedidos, clientes), Data API (acesso CRUD a recursos do merchant: catálogos, cupons, conteúdo, jobs, site preferences…) e Meta API (descrição formal da API, inclusive atributos custom).
Client ID
Identificador da aplicação cliente, criado no Account Manager. É obrigatório em toda requisição; sem ele, a resposta é 400.
OCAPI Settings
Documento JSON configurado no BM (Administration > Site Development > Open Commerce API Settings) que diz o que cada client ID pode acessar. Por padrão, nada é permitido: a resposta é 401 (UnauthorizedException).
Hook
Ponto de extensão (dw.ocapi.shop.basket.items.beforePOST etc.) implementado num cartridge e registrado no hooks.json. Executa script B2C antes, depois ou na montagem da resposta.
SCAPI
B2C Commerce API (também chamada de Salesforce Commerce API): APIs REST em OAS 3.0 servidas por um gateway com CDN, em {shortCode}.api.commercecloud.salesforce.com. Divide-se em Shopper APIs (SLAS) e Admin APIs (token do Account Manager).
SLAS
Shopper Login and API Access Service: serviço OAuth 2.1 que emite tokens de comprador (guest ou registrado) aceitos pela SCAPI e pela OCAPI Shop API.
Custom API
Endpoint REST próprio exposto pela SCAPI. É definido num cartridge (rest-apis/) com contrato OAS, script e api.json.

Status atual (2026). A documentação oficial diz que "OCAPI is marked deprecated as of April 2026", que projetos novos devem usar SCAPI exclusivamente e que, a partir de 1º de setembro de 2026, os OCAPI Settings deixam de estar disponíveis para realms de clientes novos. Não há data de EOL para a OCAPI em realms existentes. O guia do exame ainda lista a OCAPI; estude-a para a prova e use SCAPI em projetos novos.

Anatomia de uma URL OCAPI

  • Versão: v + número com underscore (v24_5 = 24.5). Cada versão define um conjunto fixo de recursos e propriedades. Versões novas podem acrescentar e depreciar, e a versão antiga continua respondendo igual. Fixe a versão no cliente.
  • Identificadores são case-sensitive e devem ser URL-encoded (foo#bar → foo%23bar). Vários IDs vão entre parênteses: (123,456).
  • Client ID: precedência Bearer token > parâmetro client_id > header x-dw-client-id.
  • Parâmetros comuns: locale, currency, expand, select, start e count (paginação), q e refine (busca).

OCAPI Settings: permissões por client ID

No BM você escolhe o tipo (Shop ou Data) e o contexto (Global ou um site) e edita o JSON. A configuração do site sobrescreve a global para aquele client ID. A maioria dos recursos da Data API é da organização e, por isso, só aceita configuração Global. As mudanças levam até 3 minutos para valer (cache).

PropriedadeSignificado
_vVersão do formato do arquivo, independente da versão da API chamada.
resource_idPadrão Ant: /products/*, /products/specific_id/images, /baskets/** (todos os sub-recursos).
methodsFiltro de métodos HTTP (obrigatório).
read_attributes / write_attributesSintaxe de property selection que limita o que sai na resposta e o que pode entrar no corpo.
cache_timeSegundos (0 a 86.400; padrão 60). Só vale para GET/HEAD de recursos cacheáveis da Shop API, e exige o Page Caching do site habilitado.
personalized_caching_enabledDesliga o cache personalizado por JWT quando a resposta não varia por cliente.
version_range{"from": "23.1", "until": "24.5"}: permissão só para um intervalo de versões (until não incluso).
configAjustes especiais: limite de ATS exposto, price books em /products/*/prices, view types de imagem.

Expansions são sub-recursos para efeito de permissão: liberar /products/* não libera /products/*/images. Para usar expand=images,prices é preciso ter permissão em cada sub-recurso.

O token é reutilizado até expirar, porque pedir um token novo por chamada é anti-padrão de performance. O client_id fica embutido no JWT (claim iss) e não precisa ser repetido.

Métodos, documentos e recursos de consulta

MétodoSemântica na OCAPI
GET / HEADLeitura; cacheáveis (Shop API).
POSTCria (ex.: cesta, item, pedido) ou executa uma action (/customers/auth).
PUTCria ou substitui: limpa as propriedades ausentes no corpo.
PATCHAtualização parcial: só mexe nas propriedades enviadas; não cria.
DELETERemove.

Clientes que só falam GET/POST usam o header x-dw-http-method-override: DELETE (ou PUT, PATCH, HEAD, OPTIONS) numa requisição POST.

select, expand, c_ e resource state

  • Batch: POST multipart com até 50 sub-requisições, cada uma com o seu método.
  • Erros: 400 (fault de validação ou Status.ERROR de um hook), 401 (token, permissão ou origem não autorizada), 404, 409 (conflito de estado), 500 (exceção não tratada em hook), 503 (HookCircuitBreakerException).
  • Meta API: GET /dw/meta/rest/shop/v24_5?client_id=… lista todos os resource_id da versão. É útil para montar os Settings.

Hooks: customizar a lógica de negócio

Recursos que modificam estado (cesta, pedido, cliente…) e vários de leitura oferecem três tipos de extension point:

TipoUsoRegras
before<METHOD>Validar ou normalizar a entradaRecebe o objeto Script API e o documento de requisição.
after<METHOD>Alterar o objeto, recalcular, chamar serviços dentro da transaçãoNão altere o documento de requisição (ele não é reprocessado).
modify<METHOD>ResponseEnriquecer ou remover campos da resposta (inclusive c_)Sem transação: modificar objetos persistentes causa ORMTransactionException e 500. Em GET com cache, só roda quando o cache está vazio ou vencido.
Convenience hooksdw.order.calculate, validateBasket, validateOrderCentralizam o cálculo da cesta em vez de duplicá-lo em cada after.

Registrando e implementando

Regras que caem na prova

  • O nome exportado é o nome do hook sem o pacote: dw.ocapi.shop.basket.items.beforePOST é exportado como beforePOST.
  • Retorne um dw.system.Status. OK deixa o processamento continuar; ERROR encerra, faz rollback e responde 400 com o código e a mensagem do status; uma exceção vira 500 com rollback.
  • Se o hook não retornar Status, outros scripts registrados para o mesmo hook (inclusive a implementação base sobrescrita) podem ser executados. Um Status não nulo encerra a cadeia.
  • Para passar dados entre hooks da mesma requisição, use request.custom (ex.: afterPOST grava o id do pagamento, modifyPOSTResponse o devolve).
  • O cartridge precisa estar no cartridge path do site. Para recursos da organização (bibliotecas, Data API), ele vai no cartridge path do Business Manager.
  • Circuit breaker: se mais de 50 das últimas 100 chamadas a um hook falharem, ele "abre" por 60 s (503 HookCircuitBreakerException) e depois testa 10 chamadas (half-open). Investigue no Log Center buscando HookCircuitBreaker.

SCAPI e SLAS: o equivalente moderno

OCAPISCAPI
HostA própria instância (/dw/shop, /dw/data)https://{shortCode}.api.commercecloud.salesforce.com/{family}/{api}/v1/organizations/{organizationId}/…
ContratoDocumentação proprietária, versões v24_5OAS 3.0; v1 com mudanças aditivas sem troca de versão (Shopper Baskets também tem v2)
Auth do compradorJWT via /customers/authSLAS (OAuth 2.1, com refresh token)
Auth administrativaOAuth do Account Manager + OCAPI SettingsToken do Account Manager com scopes (sfcc.catalogs, …) e SALESFORCE_COMMERCE_API:{realm}_{instance}
PermissõesJSON de OCAPI SettingsScopes do cliente (SLAS ou Account Manager)
CacheCache da resposta inteira (cache_time)Cache no web tier/CDN por objeto
CustomizaçãoHooks dw.ocapi.shop.*Os mesmos hooks (habilitar a feature switch de hooks no BM) + Custom APIs
  • Tipos de cliente SLAS: public (SPA como a PWA Kit, app mobile; usa authorization_code_pkce) e private (backend, BFF, storefront tradicional; usa client_credentials ou authorization_code com segredo).
  • O access token vale 30 min. O refresh token vale 90 dias (registrado) ou 30 dias (guest) em produção, e 9 dias fora de produção. Em clientes public, o refresh token é de uso único.
  • O token SLAS também é aceito pela OCAPI Shop API. Isso permite migração gradual e storefronts híbridos (SFRA + PWA, com Hybrid Auth).
  • Não misture scopes: nada de scopes de shopper em clientes do Account Manager, nem de admin em clientes SLAS.

Custom APIs (SCAPI)

Quando nenhum recurso padrão atende, a SCAPI permite publicar um endpoint REST próprio a partir de um cartridge. São três peças na pasta cartridge/rest-apis/{api-name}/ (nome em minúsculas, números e hífens):

  • URL: https://{shortCode}.api.commercecloud.salesforce.com/custom/loyalty-info/v1/organizations/{org}/customers?c_customer_id=…&siteId=RefArch.
  • Registro: acontece ao ativar a code version que contém a API. Por isso, trabalhe numa versão nova e troque quando estiver pronto.
  • Shopper × Admin: Shopper exige siteId e o esquema ShopperToken; Admin omite siteId, usa AmOAuth2 e o cartridge vai no path do Business Manager.
  • Respostas sempre em JSON; erros no formato RFC 9457 (pelo menos type). Custom APIs também têm circuit breaker.

Anti-padrões e pegadinhas de prova

Liberar "/**" com (**) para um client ID público. Libere só os recursos, métodos e atributos necessários.

Alterar objetos persistentes em modify…Response ou em hook de GET: não há transação, o que gera ORMTransactionException e 500.

Chamar serviço externo lento em hook sem timeout: as falhas acumulam e abrem o circuit breaker do hook (503 para todos).

Pedir um token novo a cada requisição. Reutilize até expirar.

  • Shop API = comprador/agente; Data API = recursos do merchant; Meta API = descrição.
  • Client ID obrigatório (400 sem ele); sem permissão nos Settings → 401 UnauthorizedException.
  • PUT substitui (limpa o que falta); PATCH é parcial.
  • Atributos custom: prefixo c_.
  • expand pede sub-recursos; select filtra propriedades.
  • Hook ERROR → 400 + rollback; exceção → 500.
  • Registro do hook: package.json → hooks.json; cartridge no path do site.

Checklist: você precisa saber

  • Montar URLs OCAPI (shop, data, meta; versão; identificador; relação; action).
  • Criar um client ID no Account Manager e configurar os OCAPI Settings (site × global, recursos, métodos, atributos, cache).
  • Obter JWT de comprador e token OAuth para a Data API.
  • Diferenciar GET, POST, PUT e PATCH; usar expand, select e c_.
  • Implementar e registrar hooks before, after e modifyResponse com o retorno de Status correto.
  • Explicar a relação OCAPI → SCAPI (SLAS, scopes, hooks compartilhados, Custom APIs) e o status de depreciação.

    2. PUT cria ou substitui e limpa propriedades ausentes; PATCH atualiza só as enviadas e não cria

    4. PUT só existe na Shop API

    4. Só para SLAS
