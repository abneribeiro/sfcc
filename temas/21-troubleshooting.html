Troubleshooting e otimização

Saber onde olhar é metade do trabalho. O B2C Commerce dá ao desenvolvedor um conjunto fixo de instrumentos: arquivos de log por tipo e nível, Log Center no realm, o Storefront Toolkit (com Request Log e Cache Info), os profilers, o Quota Status e o script debugger. Este tema organiza esses instrumentos num método e termina com a tabela consolidada de sintomas, que reúne os casos de debug de todos os temas.

Conceitos e glossário

System log
Logs da plataforma (error, warn, info, fatal, api, quota, deprecation, jobs, staging, sysevent…). Ficam sempre ativos e não são configuráveis pelo cliente.
Custom log
O que o seu código grava com dw.system.Logger: customerror, customwarn, custominfo, customdebug, customfatal, ou arquivos nomeados custom-<prefixo>-….
Categoria de log
Segundo argumento de Logger.getLogger(prefixo, categoria). Os níveis são ligados por categoria em Custom Log Settings.
Log Center
Aplicação do realm que agrega logs de todas as instâncias (PIG e SIG), com busca, dashboard, alertas, streaming e traces.
Storefront Toolkit
Ferramentas sobre o storefront : Page Info, Content Info, Search Info, Cache Info, Request Log e Preview Settings.
Quota
Limite da plataforma, com ação log_only, warn ou error (enforced: lança exceção e interrompe a operação).

Um método de troubleshooting

  1. Caracterize: é reproduzível ou intermitente? Em qual instância, site, locale e grupo de cliente? Qual URL e controller? Quando começou?
  2. Correlacione com mudanças: ativação de code version, replicação de dados ou código, import grande, edição manual em produção, limpeza de cache, mudança de preferência.
  3. Leia os sinais certos: erro com stack trace (error log e Log Center), lentidão (profilers e Service Status), dado errado (Storefront Toolkit, BM, replicação), quota (Quota Status e quota log).
  4. Isole: reproduza na sandbox com os mesmos dados (import do site) e a mesma code version. Use o debugger. Desative cartridges do path um a um.
  5. Corrija e previna: teste unitário do caso, log útil, alerta no Log Center.
  6. Antes de abrir um ticket: passos para reproduzir, horário (GMT), arquivo HAR e o dwsid da sessão.

Arquivos de log

Acesso: Administration > Site Development > Development Setup > Log files (WebDAV /on/demandware.servlet/webdav/Sites/Logs), o Log Center, ou o b2c CLI.

ArquivoConteúdo
error-*, fatal-*Erros e exceções não tratadas em scripts, templates e plataforma
warn-*Locks, avisos de slot, servlets
customerror, customwarn, custominfo, customdebug, customfatalSaída de Logger.* sem prefixo de arquivo
custom-<prefixo>-<host>-appserver-<data>.logSaída de Logger.getLogger('prefixo', 'categoria')
service-<prefixo>-…Service Framework: head, comm, log (tema 19)
quota-*Quotas de API e de objeto (avisos e violações)
deprecation-*Uso de APIs deprecated (ex.: <iscache status="off"/>)
api-*Problemas de API (pipeline dictionary, templates)
jobs-* e jobs/Status do job manager e logs por execução
staging-*Replicação de dados e de código
sysevent-*Registro de app server, ativação de code version, cartridges
Impex log/Logs de import/export e validação (catálogo, preço, estoque…)
Securitylogs/Logins no BM e eventos de segurança (retidos por 90 dias)
  • Retenção (Production e Staging): 30 dias, e 90 dias para os logs de segurança. Depois de 3 dias os arquivos vão para log_archive em gzip. Em sandboxes e Development não há política de retenção.
  • Limite: cada app server grava até 10 MB por dia em cada arquivo custom. Ao atingir o limite, aparece a linha Maximum log file size per day reached, logging suspended. e a gravação para até 00:00 GMT. Logs de sistema não têm esse limite.
  • Supressão: uma mensagem de erro ou aviso repetida mais de 10 vezes em 3 minutos é suprimida por mais 3 minutos.
  • Debug fica sempre desligado em produção. Fora dela, ele vai para a memória (alimenta o Request Log), não para arquivo.
  • Até 200 nomes de arquivo de log diferentes por dia e por app server (limite rígido).

Logging no código com dw.system.Logger

  • Prefixo de arquivo: 3 a 25 caracteres a-z A-Z 0-9 - _, sem começar nem terminar com - ou _. Use um por integração ou área: ajuda a encontrar e divide o limite de 10 MB.
  • Placeholders {0}, {1}: evitam concatenar strings quando o nível está desligado.
  • Atalhos estáticos: Logger.error(…), Logger.warn(…) etc. gravam no log custom raiz.
  • Logger.getNDC(): contexto aninhado (ex.: o número do pedido) acrescentado a todas as mensagens da thread.

Custom Log Settings (BM)

Administration > Operations > Custom Log Settings:

  • Níveis por categoria: a categoria precisa bater com a do getLogger (hierarquia separada por ponto). Por padrão, só WARN, ERROR e FATAL vão para arquivo, e info e debug ficam desligados.
  • Log to File por nível; Receive Email para FATAL.
  • Os níveis de log também podem ser ajustados dinamicamente na aba Config do Log Center.

Log Center e b2c logs

  • Acesso: pelo BM em Development Setup > Log Center, ou direto no navegador. Mostra os logs do realm inteiro (PIG e SIG).
  • Busca por período, severidade, tipo, texto e LCQL. Exemplo: buscar HookCircuitBreaker e abrir o Stack Trace UUID (tema 17).
  • Dashboard: tráfego, requisições mais pesadas, stack traces recorrentes. Alertas por e-mail, Slack, Teams ou PagerDuty. Também há streaming de logs, detecção de anomalias e traces (beta) ponta a ponta.
  • Mensagens com mais de ~7.000 caracteres são truncadas. Uma mensagem pode estar no Log Center e não no arquivo, se o arquivo já tiver atingido 10 MB.

Storefront Toolkit e Request Log

No BM: Merchant Tools > selecione o site > Toolkit (ou o link do site em Site Development). O storefront abre com os ícones do Toolkit.

FerramentaUse para
Page InfoDescobrir qual template e qual controller geram cada parte da página (o primeiro passo para achar "de onde vem isso").
Content InfoIr do componente ao produto, asset ou slot no BM.
Search InfoEntender a ordenação: sorting rule e score de cada hit.
Cache InfoVer o que está em cache (verde) ou não (vermelho), e o TTL de cada fragmento ou remote include.
Request LogVer os logs (inclusive debug e exceções) da última requisição e das seguintes, AJAX incluído. Exige o mesmo hostname no BM e no storefront.
Preview SettingsVer o site numa data e hora, num customer group, com um source code, ou numa variação de A/B test.

Script debugger

Breakpoints, step e inspeção de variáveis em sandboxes, pelo VS Code (Prophet ou a extensão oficial) ou pelas ferramentas da linha dwdebugger. Configuração no tema 15. Se o breakpoint não para, confira: a página veio do cache, o arquivo local difere da code version ativa, ou o host ou a versão do debugger estão errados.

Quotas enforced lançam exceção e interrompem a operação (no storefront, cai na página de erro). Não capture exceções de quota: evitar a violação é critério de design. Em produção, só o Support pode "suavizar" uma quota (de error para warn). Na sandbox, importe as configurações suavizadas de produção (Custom Quota Settings).

Da causa à otimização

  1. Meça com o Pipeline Profiler ou o Code Profiler e com o hit ratio dos relatórios. Escolha o controller com o maior produto hits × tempo médio.
  2. Cache primeiro: a rota pode ser cacheada? O que é pessoal pode ir para um remote include?
  3. Menos objetos tocados: troque varreduras de catálogo por ProductSearchModel, feche iterators e pagine.
  4. Menos chamadas externas: custom cache, assíncrono e timeouts curtos.
  5. Pese de novo depois do deploy e compare. Se piorou, faça rollback com a code version anterior ou com code replication Undo.

Anti-padrões e pegadinhas de prova

Logar demais em produção (dados inteiros de cesta ou pedido em info): estoura os 10 MB do dia e você fica sem log quando precisa.

Logar PII ou dados de cartão. Logue IDs técnicos (número do pedido, ID do cliente).

try/catch que engole erro sem log: o sintoma aparece longe da causa.

Capturar exceção de quota e seguir em frente. Redesenhe o código.

  • Logs custom: Logger.getLogger(prefixo, categoria) → custom-prefixo-*.log; níveis em Custom Log Settings.
  • Logs de todas as instâncias num lugar só: Log Center.
  • Logs da requisição atual, no storefront: Request Log (Storefront Toolkit).
  • Qual template ou controller gerou isso: Page Info. Está em cache: Cache Info.
  • Onde o tempo é gasto: Pipeline Profiler e Code Profiler.
  • Limites: Quota Status e quota-*.log.

Checklist: você precisa saber

  • Aplicar um método: caracterizar, correlacionar com mudanças, isolar, corrigir e prevenir.
  • Identificar o log certo para cada problema e conhecer retenção e limites.
  • Escrever logs úteis com Logger (prefixo, categoria, placeholders, isDebugEnabled) e configurá-los no BM.
  • Usar o Log Center, o b2c CLI, o Storefront Toolkit e o Request Log.
  • Usar o Pipeline Profiler, o Code Profiler, o Quota Status e o Service Status para otimizar.
  • Usar a tabela de sintomas de cada área.

Questões de fixação

  1. Um desenvolvedor usa Logger.getLogger('payment', 'adyen').info(...), mas nada aparece em arquivo na Staging. Qual a causa mais provável?

    1. Logs custom não funcionam em Staging
    2. O nível INFO da categoria adyen não está habilitado com "Log to File" em Custom Log Settings
    3. O prefixo precisa começar com "custom"
    4. Falta reindexar
    ver resposta

    b. Por padrão só WARN, ERROR e FATAL vão para arquivo.

  2. Qual ferramenta mostra qual template e qual controller renderizam um trecho do storefront?

    1. Log Center
    2. Storefront Toolkit › Page Info
    3. Quota Status
    4. Code Profiler
    ver resposta

    b.

  3. Um erro acontece só em Production e é preciso ver o stack trace de vários app servers. Onde?

    1. Script debugger
    2. Log Center
    3. Request Log
    4. Preview Settings
    ver resposta

    b. O Log Center agrega todas as instâncias e app servers do realm. O debugger e o Request Log olham uma requisição ou sessão por vez.

  4. Às 14h os logs custom pararam com "Maximum log file size per day reached". O que fazer?

    1. Pedir ao Support para aumentar
    2. Reduzir o volume (níveis, placeholders, menos dados) e separar por prefixos; a gravação volta às 00:00 GMT
    3. Reiniciar a instância
    4. Usar console.log
    ver resposta

    b. O limite é 10 MB por arquivo, por app server e por dia.

  5. Após um deploy, a PLP ficou lenta. Qual a primeira ferramenta para localizar o script culpado?

    1. Search Info
    2. Pipeline Profiler ou Code Profiler
    3. Security log
    4. Data Replication
    ver resposta

    b. Comece por hits × tempo médio e depois desça até a função ou linha.

  6. Uma quota enforced está sendo excedida no storefront. O que é correto?

    1. Capturar a exceção e continuar
    2. Redesenhar o código para não exceder; em produção, só o Support pode suavizar a quota
    3. Desligar a quota no BM
    4. Ignorar
    ver resposta

    b.
