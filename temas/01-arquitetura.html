Arquitetura do B2C Commerce

Antes de escrever uma linha de controller, você precisa saber onde o código roda, como ele chega lá e por que os dados que você mexe numa instância podem sumir na próxima replicação. Este tema monta o mapa mental de toda a plataforma: realm, grupos de instâncias, replicação, sandboxes, o caminho de um request do navegador até o banco e o motor de script que executa o seu JavaScript.

Conceitos e glossário

O B2C Commerce (o antigo Demandware) é um SaaS multi-tenant. Você não administra servidores, sistema operacional, banco de dados, balanceador de carga nem CDN. A Salesforce hospeda, escala e atualiza a plataforma, e você entrega duas coisas:

  • Código, empacotado em cartridges: controllers, scripts, templates ISML, forms, recursos estáticos, metadados de Page Designer.
  • Dados e configuração: catálogos, price books, inventário, conteúdo, promoções, preferências, definições de objetos, jobs, serviços.

Essa separação aparece em toda a arquitetura. Código e dados seguem caminhos diferentes, versionam de jeitos diferentes e são promovidos entre ambientes por processos diferentes.

Glossário essencial

Realm
O conjunto de todas as instâncias de um cliente. É identificado por um código de quatro letras (por exemplo zzpq), que aparece nos hostnames e nos IDs de sandbox (zzpq-001). Um cliente pode ter mais de um realm (por região, por exemplo).
Instância
Um ambiente completo e isolado: tem o seu próprio esquema de banco de dados, o seu file system compartilhado (cartridges, imagens, logs) e o seu Business Manager. Duas instâncias nunca compartilham dados, a não ser por replicação ou import/export.
PIG
Primary Instance Group. As três instâncias "oficiais" do realm: Staging, Development e Production. A replicação só acontece dentro do PIG, sempre a partir de Staging.
SIG
Secondary Instance Group. As sandboxes dos desenvolvedores. Hoje são On-Demand Sandboxes (ODS), criadas e destruídas por API ou CLI. Ficam fora da replicação.
POD / Hyperforce
O POD era o cluster físico, num data center da Salesforce, que hospedava vários realms. Os realms estão migrando para o Hyperforce, a infraestrutura em nuvem pública da Salesforce. O POD importa para o desenvolvedor em detalhes como IPs de saída (allowlists em firewalls de parceiros) e janelas de manutenção.
Organization
Nível acima dos sites dentro de uma instância. Preferências globais (Global Preferences), objetos com escopo de organização e configurações como locales ativos vivem aqui.
Site
Uma loja (storefront) dentro da instância. Uma instância pode ter vários sites, cada um com cartridge path, catálogo, price books, inventário e preferências próprios.
Business Manager (BM)
A interface administrativa web de cada instância, em https://<host>/on/demandware.store/Sites-Site. Merchandisers, administradores e desenvolvedores usam o BM.
Code version
Um diretório nomeado no servidor (por exemplo release_2026_10) com um conjunto de cartridges. Só uma code version fica ativa por instância.
Compatibility mode
A versão da API de script com que uma code version roda (por exemplo 22.7). Define recursos de linguagem (ES6+) e comportamentos de API.
Storefront
A loja que o comprador vê. Pode ser renderizada no servidor (SFRA, SiteGenesis) ou num front-end headless (PWA Kit, Storefront Next) que consome APIs.

Se uma alternativa fala em "replicar de Staging para a sandbox", é distrator. A documentação diz: "You can't use replication to copy data from staging to a developer sandbox". Para levar dados a uma sandbox, exporte de Staging e importe na sandbox.

Quem usa cada instância

  • Desenvolvedor: Sandbox e Staging. Escreve e testa na sandbox e é responsável pelo upload de código em Staging. Pode exportar de Staging os dados criados pelos merchandisers para usar como massa de teste nas sandboxes. Não desenvolve em Development.
  • Merchandiser: Staging. Cria campanhas e promoções, gerencia produtos, configura a busca.
  • QA: Development, em condições o mais próximas possível de Production.
  • Administrador: todas. Concede acessos, reinicia instâncias, gerencia feeds de dados, faz upload de certificados.

Replicação de dados e de código

Replicação é o mecanismo que promove o que foi preparado em Staging para Development ou Production. Há dois processos independentes, e os dois são criados e executados em Staging (até o Publishing e o Undo, que só afetam o destino).

Data Replication

Copia dados, metadados e arquivos. Funciona em dois níveis:

  • Global: configuração da organização inteira (custom object types, preferências globais, catálogos, price books, bibliotecas compartilhadas, OCAPI settings globais, static content…).
  • Site: dados de um ou mais sites (campanhas, slots, conteúdo da biblioteca privada, preferências do site, índices de busca, shipping, taxação, URLs de SEO…).

Os dados selecionados substituem os correspondentes no destino. Se Staging e Development têm os catálogos A, B e C, e em Staging você atualiza B, apaga C e cria D, replicar "Catalogs" deixa Development assim: A intocado, B atualizado, C apagado, D criado. O que não foi selecionado não muda.

Tipo de processoO que faz
TransferCopia os dados para o destino sem afetar os dados em uso lá. Precisa de um Publishing depois.
Transfer & PublishingCopia e substitui imediatamente.
PublishingPublica o que foi transferido antes. As tarefas precisam ser exatamente as mesmas do Transfer. Desligue a indexação incremental durante o Publishing.
UndoReverte o destino ao estado anterior à última replicação publicada. Só vale para a última, e não atravessa uma GA release (um processo de 24.7 não pode ser desfeito em 24.8).

O que a replicação de dados não leva

A documentação lista o que precisa ser criado ou importado diretamente em cada instância. Estes itens caem muito em prova:

  • Clientes e atribuições a customer groups; pedidos e informações de pedido; gift certificates; dados de pagamento
  • Inventário; active data; sitemaps; redemptions de source code
  • Usuários, roles e permissões; o perfil da organização
  • Job schedules e histórico; batch processes; feeds de importação de catálogo e conteúdo
  • Custom error pages; arquivos enviados mas não importados

Ordem e dependências

  1. A primeira replicação para cada destino é uma replicação global completa; não dá para escolher tarefas nessa primeira vez.
  2. Alterou um system object type ou criou um custom object type? Replique Custom Object Types (definições) antes de qualquer objeto daquele tipo.
  3. Campanhas dependem de source codes, customer groups e coupons: replique-os antes ou junto, sob risco de corromper dados.
  4. Catálogos para produção vão junto com os índices de busca. Reconstrua o índice antes, espere terminar e desligue a indexação incremental e as reconstruções agendadas durante a replicação.
  5. Teste cada processo de Staging para Development antes de levar para Production, e não rode dois processos ao mesmo tempo.
  6. Em Production, faça primeiro Transfer, confira os logs e só então Publishing; agende para horários de pouco tráfego, porque replicar consome recursos.

Code Replication

Transfere uma code version de Staging para Development ou Production e pode ativá-la no destino. Os tipos são Transfer, Activation, Transfer & Activation e Undo. O Undo reativa a code version que estava ativa antes. Em sandboxes não há code replication: o código chega por upload (WebDAV ou CLI) e é ativado em Administration > Site Development > Code Deployment.

Nunca edite dados replicáveis nem o cartridge path direto em Production. A próxima replicação de Staging apaga essas alterações (o "drift" entre ambientes), e mudanças de código ou cartridge path feitas lá podem gerar versões diferentes da mesma página. Toda alteração nasce em Staging.

Custom objects criados em Production (log de webhooks, por exemplo) sumiram depois de uma replicação? O tipo estava como replicável e a tarefa de custom objects sobrescreveu os registros. Dados que nascem em Production precisam de um tipo marcado como Not Replicable. Veja o tema 13.

On-Demand Sandboxes

A sandbox é a sua instância pessoal de desenvolvimento. As On-Demand Sandboxes (ODS) rodam em nuvem pública e são criadas sob demanda por uma API self-service. Na prática:

  • Créditos: o realm compra créditos. Uma sandbox ligada consome créditos de uptime por minuto (o perfil medium, padrão, consome 1 crédito por minuto; large e xlarge consomem mais). Desligada, consome 0,3 crédito por minuto. Apagada, não consome.
  • TTL: na criação dá para definir um time-to-live em horas, e a sandbox é apagada sozinha quando ele vence (0 significa infinito, se o realm permitir).
  • Nasce vazia: sem código e sem dados. Você faz upload do código e importa os dados (o site de demonstração do SFRA, ou um export de Staging).
  • Permissões: a gestão passa pelo Account Manager (role Sandbox API User), e na criação você define as permissões de OCAPI e WebDAV para o seu client ID.
  • Sem replicação: a SIG não participa da replicação.

O caminho de um request

Entender a infraestrutura de uma instância de Production explica o comportamento de cache, sessão e performance. Os componentes, segundo a documentação de troubleshooting de infraestrutura:

eCDN
CDN embutido (embedded CDN). Serve conteúdo a partir de pontos próximos ao comprador, absorve picos de tráfego e oferece WAF e HSTS. Cacheia conteúdo estático na borda.
Firewall / load balancer
Controla o que entra e sai e distribui os requests entre os web servers.
Web server + Web Adapter
O Web Adapter é um plugin proprietário do web server. Ele cuida do page cache, monta a página a partir de remote includes e distribui a carga entre os application servers. Production tem pelo menos dois web servers.
Application servers
Executam a lógica de negócio e a apresentação (controllers, scripts, ISML). Production tem pelo menos dois.
Banco e file system
Todos os application servers de uma instância usam o mesmo esquema de banco de dados e o mesmo file system compartilhado (cartridges, imagens, logs). Instâncias diferentes usam esquemas diferentes.

Afinidade de sessão

Web servers e Web Adapter são stateless: o load balancer distribui os requests de uma sessão entre eles aleatoriamente. Já os application servers são session-aware: guardam atributos de sessão, autenticação e dados de formulário. Por isso, todos os requests de uma sessão vão para o mesmo application server. O Web Adapter cria o session ID no primeiro request e o guarda no cookie sid; o valor codifica, entre outras coisas, qual application server foi escolhido.

Request ID e remote includes

Cada request recebe do Web Adapter um request ID, que aparece nos logs. Cada remote include é um request adicional ao application server, com cache próprio. O ID dele estende o do request principal no formato requestID-profundidade-número:

É assim que uma página de categoria fica cacheada por 24 horas enquanto o minicart (um remote include sem cache) mostra a cesta de cada comprador. O detalhe de implementação está nos temas 10 (ISML) e 20 (performance).

Dois caches

  • Static content cache: imagens, CSS, JS. Tem TTL configurável, e as URLs carregam um fingerprint (o v1729612345678 do exemplo anterior) que muda quando você ativa outra code version.
  • Page cache: HTML gerado a partir de ISML quando a resposta declara cache (<iscache> ou, no SFRA, o middleware de cache). Só funciona com a preferência de page cache ligada no BM, e é invalidado por expiração, por replicação ou por limpeza manual no BM.

O motor de script

O JavaScript do servidor roda num interpretador baseado no Rhino (JavaScript sobre a JVM), dentro do application server. Não é Node.js. Isso tem consequências práticas:

  • Não existe npm install em runtime, nem fs, process, setTimeout ou fetch. Você usa as APIs dw.* (dw.net.HTTPClient e o Service Framework para HTTP, dw.io.File para arquivos na área IMPEX, e assim por diante).
  • Os módulos seguem CommonJS: require('dw/system/Logger'), require('*/cartridge/scripts/helpers/x'), module.exports.
  • Cada request é isolado: um script não guarda estado entre execuções. Para manter estado use a sessão (session.custom e session.privacy), objetos persistentes (custom objects ou atributos) ou cookies.
  • Há timeouts de script e quotas de API (número de objetos, tamanho de coleções, chamadas por request). Estouro de quota pode quebrar o request; isso fica para o tema 20.

Compatibility mode e recursos de linguagem

Cada code version declara um compatibility mode (10.4 a 22.7). Ele decide o dialeto de JavaScript e alguns comportamentos da API. Você descobre o modo ativo com System.getCompatibilityMode(), que devolve um número (22.7 vira 2207).

ModoO que muda (resumo da documentação)
< 21.2ECMAScript 5.
21.2Parte do ES6+: let/const com escopo de bloco, arrow functions, for…of, generators, destructuring de objetos, Map, Set, Symbol, typed arrays, métodos novos em String/Array/Object. Shorthand de propriedades ainda não. Novas palavras reservadas (class, import, export…).
22.7Mais ES6+: shorthand de propriedades, template literals, bigint, globalThis, operador **, Object.values e Object.entries.

Sandboxes e a instância Development reportam o mesmo tipo, System.DEVELOPMENT_SYSTEM (0). Para separar "sandbox" de "development", não use o tipo de instância: use credenciais de serviço ou preferências diferentes por instância (o próximo capítulo mostra como).

Código consciente do ambiente

O mesmo código roda em todas as instâncias, porque a code version ativa em Production é exatamente a que foi testada em Staging. Então o código não pode carregar endpoints, credenciais nem chaves fixas. O que muda por instância deve vir da configuração de cada instância.

Anti-padrões e pegadinhas de prova

Identificar o ambiente pelo hostname. if (request.httpHost === 'www.acme.com') quebra com aliases, eCDN, domínio novo ou um teste em Development. Use configuração por instância.

Editar catálogo ou conteúdo em Production. A próxima Data Replication sobrescreve. A única exceção aceita é um hotfix emergencial, que também precisa ser refeito em Staging.

Teste de carga em Staging. Staging não tem cache e faz checagem completa de file system; não representa Production.

  • "Onde o merchandiser deve editar?" → Staging.
  • "Como popular uma sandbox com dados de Staging?" → export em Staging + import na sandbox (site export/import, ou jobs).
  • "O que não é replicado?" → clientes, pedidos, inventário, usuários e roles, job schedules, gift certificates, active data.
  • "Desfazer uma replicação de dados?" → Undo, que só vale para a última. Para código, Code Replication Undo, ou reativar a versão anterior.
  • "Onde o Storefront Toolkit não existe?" → Production.
  • "Quem monta a página a partir de remote includes?" → o Web Adapter.

Questões de fixação

  1. Um merchandiser alterou a descrição de 200 produtos diretamente em Production. Dois dias depois as descrições voltaram ao valor antigo. O que aconteceu?

    1. O page cache expirou
    2. Uma Data Replication de Staging com a tarefa Catalogs sobrescreveu os dados
    3. A sandbox sincronizou com Production
    4. O índice de busca foi reconstruído
    ver resposta

    b. A replicação substitui no destino os dados das tarefas selecionadas. Edições em Production são sobrescritas na próxima replicação de catálogo. Sandboxes não participam da replicação.

  2. Como popular uma On-Demand Sandbox nova com o catálogo e o conteúdo de Staging?

    1. Criar um Data Replication com target = sandbox
    2. Code Replication com "Transfer & Activation"
    3. Exportar em Staging (site export ou jobs de export) e importar na sandbox
    4. Clonar Production
    ver resposta

    c. A replicação só vale dentro do PIG. Dados chegam às sandboxes por export e import.

  3. Qual destes itens a Data Replication não leva de Staging para Production?

    1. Price books
    2. Slot configurations
    3. Registros de inventário
    4. Custom object types
    ver resposta

    c. Inventário não é replicado (assim como clientes, pedidos, usuários, job schedules e gift certificates). O inventário chega a Production por import, normalmente num job alimentado pelo ERP.

  4. Você precisa replicar uma campanha nova que usa coupons e um source code group novos. Qual é a ordem segura?

    1. Campaigns primeiro e depois Coupons e Source Codes
    2. Coupons e Source Codes antes ou junto de Campaigns
    3. Tanto faz
    4. Só Campaigns; os dependentes vão automaticamente
    ver resposta

    b. As best practices dizem para replicar source codes e coupons antes ou junto das campanhas que os usam, sob risco de corromper dados.

  5. Quem monta uma página composta por remote includes com políticas de cache diferentes?

    1. O application server, num único request
    2. O Web Adapter, que faz um request por include e junta as partes
    3. O navegador, com JavaScript
    4. O eCDN
    ver resposta

    b. Cada remote include é um request adicional ao application server, cacheado separadamente; o Web Adapter monta a página.

  6. Em que instância o Storefront Toolkit fica desabilitado?

    1. Sandbox
    2. Staging
    3. Development
    4. Production
    ver resposta

    d. A tabela oficial de instâncias diz que o Storefront Toolkit é desabilitado em Production.

  7. Um script precisa usar arrow functions e Map. Qual é o compatibility mode mínimo?

    1. 18.10
    2. 19.10
    3. 21.2
    4. Qualquer um; o Rhino sempre suportou
    ver resposta

    c. A partir de 21.2 o motor aceita parte do ES6+ (arrow functions, for…of, Map/Set, destructuring). Template literals e shorthand de propriedades chegam em 22.7.

  8. Todos os requests de uma mesma sessão de comprador são atendidos por…

    1. O mesmo web server
    2. O mesmo application server
    3. Qualquer application server, porque a sessão fica no banco
    4. O eCDN
    ver resposta

    b. Web servers são stateless; application servers são session-aware, e a afinidade de sessão leva todos os requests da sessão ao mesmo app server.
