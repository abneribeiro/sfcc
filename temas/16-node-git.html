Node e Git no fluxo SFCC

O storefront não roda em Node, mas todo o resto do trabalho do desenvolvedor passa por ele: dependências, build de JS e SCSS, lint, testes unitários, upload e automação de deploy. E o Git é a fonte da verdade do código e da configuração versionável (metadados, preferências, jobs). Este tema mostra como os dois se encaixam num projeto B2C Commerce profissional, do npm install ao pipeline que publica uma code version em Staging.

Conceitos e glossário

Node.js no SFCC
Ambiente local e de CI para ferramentas. A documentação do SFRA é clara: "B2C Commerce uses Node.js only for npm dependency management." O servidor executa o motor de script da plataforma.
package.json (raiz)
Scripts npm, dependências de build e teste e, no SFRA, paths para outros cartridges.
sgmf-scripts
CLI que encapsula webpack (JS e SCSS), ESLint, Stylelint, mocha e dwupload.
proxyquire
Biblioteca que substitui os require de um módulo por mocks, para testar scripts que dependem de dw/* fora do servidor.
Code version de release
Nome da pasta de código gerado no CI (ex.: release-2026-11-04-1530), que liga um commit do Git ao que está rodando.

Node e npm no projeto

  • Versão: a documentação do SFRA cita o Node 18 como testado; a GitHub Action oficial do B2C CLI usa o Node 22 por padrão. Fixe a versão do projeto num .nvmrc (ou no campo engines) e use a mesma no CI.
  • npm install × npm ci: install resolve e pode atualizar o lockfile (uso local); ci instala exatamente o package-lock.json (uso no CI, builds reprodutíveis).
  • Rode npm install a cada versão nova do SFRA: as dependências do base mudam entre versões.
  • Nenhum pacote npm vai para o servidor. Uma biblioteca que você quer usar no servidor precisa ser compatível com o motor da plataforma e ser copiada para dentro de um cartridge, como módulo CommonJS.

Integração e funcionais

  • Integração (npm run test:integration): requests HTTP reais a uma sandbox (request-promise, chai), que validam rotas e JSON. Precisam do dw.json (ou de parâmetros) e de dados importados.
  • Funcionais/E2E: navegador automatizado (webdriver.io, codeceptjs) percorrendo PDP, carrinho e checkout. Caros; rode os fluxos críticos (happy path).

Git: estrutura e o que versionar

E o SFRA base?

O app_storefront_base não se edita. As opções comuns: (a) repositório irmão clonado na tag certa, como a documentação descreve; (b) cópia do base num diretório vendor/ do repositório, atualizada só em upgrades (commit "chore: SFRA v7.x.y"). Qualquer alteração no base aparece como diff e é um alerta.

A documentação de boas práticas recomenda não versionar zips de cartridges (o Git não rastreia mudanças dentro deles) e versionar o conteúdo de exports de configuração. Exports do BM são ordenados, então diffs entre exports revelam mudanças reais.

Branches, revisões e releases

  • Uma sandbox por desenvolvedor (feature branches) e uma sandbox de integração (o "Build/Merge" da documentação) para develop.
  • Pull requests com revisão e o CI (lint + testes + build) obrigatórios.
  • Releases viram tags no Git e code versions nomeadas em Staging (ex.: v2026-11-0): qualquer versão em produção é rastreável até um commit.
  • Hotfix: branch a partir da tag em produção, code version nova, replicação, merge de volta em develop.
  • Mudanças de metadados (atributos, preferências, CO types) vão no mesmo PR do código que as usa, na pasta metadata/, e são importadas no deploy.

CI/CD com a GitHub Action oficial

O projeto B2C Developer Tooling publica GitHub Actions oficiais (setup, code-deploy, data-import, job-run, webdav-upload e um passthrough para qualquer comando). Credenciais ficam em secrets e configuração não sensível em variables.

Os nomes das actions e das entradas (code-version, activate) seguem o guia CI/CD with GitHub Actions do B2C Developer Tooling (actions @v2). Confira a entrada exata do data-import na versão que você usar. Uploads para Staging também exigem o certificado de cliente da organização (2FA), configurado no runner.

Etapas típicas de um pipeline completo: install → lint → unit tests → build → deploy (code version nova) → import de metadados → activate → smoke test (integração ou E2E curtos) → notificação. A replicação de Staging para Production é um passo separado, com aprovação.

Anti-padrões e pegadinhas de prova

Achar que o Node roda o storefront ou que pacotes npm ficam disponíveis no servidor.

Segredos no repositório (dw.json, .env, chaves em YAML).

Deploy manual do computador de um dev para Staging, sem rastreio de qual commit está em qual code version.

Testes que dependem de uma instância para lógica pura (cálculos, transformações). Isole em helpers e teste com proxyquire.

  • Node no SFCC → gerenciar dependências e ferramentas (build, lint, testes, upload).
  • Testes de models/helpers: mocha + chai + sinon + proxyquire; controllers: integração; views: funcionais.
  • Compilar JS: npm run compile:js; SCSS: npm run compile:scss.
  • Repositórios SFRA clonados lado a lado e na mesma tag.

Checklist: você precisa saber

  • Explicar o papel do Node (tooling) e gerenciar a versão e as dependências.
  • Usar os scripts npm do SFRA: compile, lint, test, cover, integration, upload, watch.
  • Escrever testes unitários com proxyquire, inclusive para código com module.superModule.
  • Organizar o repositório (cartridges, metadados, testes) e o .gitignore.
  • Definir um fluxo de branches, PRs e releases ligado a code versions.
  • Montar um pipeline de CI/CD com o b2c CLI ou as actions oficiais.

    4. Rodar jobs

  2. Como testar um helper que usa require('dw/catalog/ProductMgr') fora do servidor?

    1. Não é possível
    2. Com proxyquire, substituindo o require por um mock
    3. Instalando dw pelo npm
    4. Só com testes de integração
    ver resposta

    b. É o padrão dos testes unitários do próprio SFRA.

  3. Que tipo de teste a documentação do SFRA associa a controllers?

    1. Unitário
    2. Integração
    3. Funcional
    4. Nenhum
    ver resposta

    b. Models: unitários; controllers: integração; views: funcionais.

  4. O que não deve ser versionado?

    1. metadata/meta/*.xml
    2. dw.json com credenciais
    3. package-lock.json
    4. Testes
    ver resposta

    b. Os metadados e o lockfile devem estar no repositório.

  5. Por que nomear a code version com branch e data (ou tag) no CI?

    1. É exigência do WebDAV
    2. Para rastrear qual commit está em cada instância e permitir rollback
    3. Para acelerar o upload
    4. Para evitar quotas
    ver resposta

    b. Combina com a boa prática de uma code version nova por deploy.
