B2C Commerce Script e APIs dw.*

Toda lógica de negócio do servidor (controllers, helpers, hooks, jobs, models) é escrita em B2C Commerce Script: JavaScript executado pelo motor da plataforma, com acesso à Script API (dw.*) para ler e gravar catálogo, cestas, pedidos, clientes, conteúdo e configuração. Este tema ensina a usar essa API com segurança: os pacotes principais, transações, coleções e iteradores, preferências, sessão, valores monetários, tratamento de erros, e como organizar o código em helpers e models reutilizáveis.

Conceitos e glossário

B2C Commerce Script
JavaScript baseado no Rhino, rodando no application server, com extensões da plataforma. O dialeto depende do compatibility mode (ES5; parte do ES6+ a partir de 21.2 e 22.7; veja o tema 01).
Script API
As classes dw.* e o pacote TopLevel (Object, Array, Error, require, empty()…). Documentação de referência: B2C Commerce Script API.
.js × .ds
.ds é a extensão histórica dos scripts usados em pipelines (com importPackage e anotações @input/@output). Código novo é .js com require.
Business object
Objeto persistente da plataforma (Product, Order, Profile, CustomObject…). Gravar nele exige transação.
Manager
Classe estática de entrada de um domínio: ProductMgr, CatalogMgr, BasketMgr, OrderMgr, CustomerMgr, PromotionMgr, ContentMgr, CustomObjectMgr, ShippingMgr, PaymentMgr…
Quota
Limite de uso de API por request (objetos criados, tamanho de coleções, chamadas). Detalhes no tema 20.

Transações

Pela documentação de dw.system.Transaction, uma transação fornece o contexto para mudanças atômicas em business objects persistentes. Antes de criar, alterar ou apagar um objeto, é preciso iniciar uma transação; as mudanças só se tornam definitivas no commit, e um rollback devolve os objetos ao estado anterior. Leituras não precisam de transação.

FormaUso
Transaction.wrap(fn)Executa fn entre begin e commit. Se o commit falhar, faz rollback e lança exceção. Retorna o retorno de fn. É a forma preferida.
Transaction.begin() / commit() / rollback()Controle manual (ex.: decidir rollback por regra de negócio). Aninhamentos precisam de commits simétricos.

Iteração e limites de transação

O guia Understanding Server-Side JavaScript descreve dois métodos para atualizar muitos objetos:

  1. Uma transação por objeto (recomendado): busque e atualize cada objeto em transação própria. Mais robusto; uma falha afeta só aquele objeto.
  2. Tudo numa transação: só para poucos objetos e quando precisa ser "tudo ou nada". A transação pode ficar grande demais (limite de tamanho, muitos recursos) e o commit pode falhar por concorrência, e então nada é gravado.

Leia o objeto na mesma transação que o altera; caso contrário, a plataforma recusa a gravação de dados velhos (stale). Em jobs, o modelo chunk-oriented faz isso por você: uma transação por chunk (tema 18).

Nem todo objeto pode ser gravado em qualquer contexto. Pelas Object Quotas oficiais, são somente leitura em requests de storefront: produtos, catálogos, categorias, price books, inventory lists, promoções, campanhas, conteúdo, site e organization preferences, shipping methods, stores e custom objects replicáveis, entre outros. No storefront se grava em basket, order, customer/profile e em custom objects não replicáveis. O resto é atualizado por jobs, imports ou BM.

  • Alterou um business object fora de transação → exceção.
  • Transaction.wrap devolve o retorno do callback e faz rollback automático se o commit falhar.
  • Algumas APIs controlam a própria transação e não podem ser chamadas dentro de uma (ex.: Basket.reserveInventory()).
  • Nos hooks de OCAPI/SCAPI, a plataforma já abre a transação: não abra outra.

Coleções e iteradores

As APIs devolvem coleções da plataforma (dw.util.Collection, List, Map, Iterator), que se comportam como objetos Java, não como arrays JavaScript. Os jeitos de percorrê-las:

Um script não guarda estado entre execuções: todas as variáveis são descartadas no fim do request. Para persistir, a documentação lista sessão, business objects persistentes e cookies. Valores guardados na sessão precisam ser de tipos suportados (primitivos); desde o compatibility mode 19.10, tipos não suportados geram exceção.

Money, Quantity e formatação

Preços e totais são dw.value.Money (valor + moeda), nunca Number soltos. Isso evita somar BRL com USD e mantém o arredondamento da plataforma.

dw.value.Quantity carrega valor e unidade (usado em getPrice(quantity), nas quantidades de line items e no ATS). Datas usam dw.util.Calendar e StringUtils.formatCalendar(cal, 'yyyy-MM-dd'); o fuso padrão é o da instância (System.getInstanceTimeZone()), e o do site está em Site.getCurrent().getTimezone().

Erros, exceções e Status

Além dos erros padrão do ECMAScript (TypeError, ReferenceError…), a plataforma mapeia exceções Java para classes próprias: IOError (I/O, incluindo SOAP), Fault (RPC), XMLStreamError, SystemError (o resto) e APIException (erros de API com type, como CreateOrderException). Erros Java como OutOfMemoryError não podem ser capturados.

dw.system.Status é o retorno padrão de muitas APIs e hooks: Status.OK ou Status.ERROR, com código, mensagem e detalhes.

O timeout padrão de script é de 30 segundos (guia de boas práticas). Chamadas HTTP feitas pelo script herdam esse teto, e é por isso que integrações usam os timeouts do Service Framework (tema 19).

Exemplo completo: "lojas próximas com estoque"

StoreMgr.searchStoresByPostalCode(countryCode, postalCode, distanceUnit, maxDistance) devolve um LinkedHashMap de loja para distância, ordenado da mais próxima para a mais distante. O centro da busca vem das geolocations cadastradas na instância: sem uma geolocation para aquele CEP, o mapa volta vazio. Store.inventoryListID fica vazio se a loja não tiver uma inventory list atribuída.

Boas práticas da Script API

  • Busca via índice (ProductSearchModel) no storefront; queryAllSiteProducts só em jobs.
  • Evite chamadas de API dentro de loops grandes; prefira APIs que devolvem coleções e pagine (asList(start, size)).
  • Feche os SeekableIterators.
  • Transações curtas, só para escrita.
  • require preguiçoso dentro das funções.
  • Nada de estado global (variáveis de módulo mutáveis): cada request é isolado, e o comportamento de cache de módulos não é contrato.
  • Configuração fora do código: preferências, Service Credentials, custom objects de configuração.
  • Log com categoria e sem dados sensíveis (tema 21).
  • Prefira a API a pipelets, e require a importPackage.

Anti-padrões e pegadinhas de prova

Gravar fora de transação (product.custom.x = 1 sem Transaction.wrap): exceção.

Uma transação gigante num loop de milhares de objetos: risco de estourar o tamanho e de falhar por concorrência. Use uma transação por objeto ou um job chunk-oriented.

Não fechar o SeekableIterator, ou convertê-lo inteiro em lista sem paginar.

Somar Number para valores monetários em vez de Money: erros de arredondamento e mistura de moedas.

  • "Qual API para escrever com rollback automático?" → Transaction.wrap.
  • "Ler uma preferência custom do site" → Site.getCurrent().getCustomPreferenceValue('id').
  • "Ler uma preferência global" → System.getPreferences().getCustom().
  • "Dados da sessão apagados no logout" → session.privacy (SFRA: privacyCache).
  • "Iterador de consulta grande" → SeekableIterator, que precisa de close().
  • "Timeout padrão de script" → 30 segundos.

Checklist: você precisa saber

  • Reconhecer os pacotes dw.* principais e os managers de cada domínio.
  • Importar com require e evitar globais, importPackage e pipelets.
  • Usar Transaction.wrap, begin/commit/rollback e escolher a estratégia de transação em loops.
  • Percorrer coleções (iterator, toArray, utilitário do SFRA) e fechar SeekableIterator.
  • Ler preferências de site e de organização, sessão e locale.
  • Calcular com Money e Quantity e formatar com StringUtils.
  • Tratar erros (tipos da plataforma, APIException, Status).
  • Organizar a lógica em helper, model, decorator, factory e service.

Questões de fixação

  1. Qual destes trechos grava corretamente um atributo custom de um produto?

    1. product.custom.badge = 'novo';
    2. Transaction.wrap(function () { product.custom.badge = 'novo'; });
    3. Transaction.begin(); product.custom.badge = 'novo';
    4. ProductMgr.save(product)
    ver resposta

    b. Escritas exigem transação. A opção c nunca faz commit.

  2. Um job atualiza 50 mil custom objects. Qual estratégia o guia oficial recomenda?

    1. Uma única transação para todos
    2. Atualizar cada objeto na sua própria transação (ou usar um step chunk-oriented)
    3. Sem transação
    4. Uma transação por request HTTP
    ver resposta

    b. Uma transação gigante pode exceder o tamanho permitido e falhar por concorrência, sem gravar nada.

  3. O que fazer com o retorno de CustomObjectMgr.queryCustomObjects(...) depois de usá-lo?

    1. Nada
    2. Chamar close()
    3. Chamar commit()
    4. Atribuir null
    ver resposta

    b. É um SeekableIterator; feche-o, de preferência num finally.

  4. Como ler uma preferência custom enableGiftWrap do site atual?

    1. System.getPreferences().getCustom().enableGiftWrap
    2. Site.getCurrent().getCustomPreferenceValue('enableGiftWrap')
    3. session.custom.enableGiftWrap
    4. Resource.msg('enableGiftWrap')
    ver resposta

    b. A opção a lê preferências de organização (globais).

  5. Onde guardar um dado do comprador que precisa sumir quando ele faz logout?

    1. session.custom
    2. session.privacy (SFRA: req.session.privacyCache)
    3. Variável global do módulo
    4. Cookie sem expiração
    ver resposta

    b. Os atributos de privacidade da sessão são limpos no logout; os custom duram a sessão inteira.

  6. Por que preferir dw.value.Money a números para valores?

    1. É mais rápido
    2. Carrega a moeda, impede misturar moedas e mantém o arredondamento da plataforma
    3. É obrigatório no ISML
    4. Serializa melhor
    ver resposta

    b. Operações como add e subtractPercent devolvem novos Money na mesma moeda.
