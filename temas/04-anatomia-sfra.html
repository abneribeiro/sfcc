Anatomia do SFRA

O Storefront Reference Architecture é o blueprint oficial de storefront renderizado no servidor. Antes de estendê-lo (temas 06 e 08), você precisa saber onde cada coisa mora: as camadas da pilha de cartridges, o módulo server, os models, os templates, o JavaScript e o SCSS de cliente, como uma página nasce de uma URL, como a busca e o checkout se organizam, e o que acontece com tudo isso quando sai uma versão nova do SFRA ou da plataforma.

Conceitos e glossário

app_storefront_base
O cartridge base do SFRA, mantido pela Salesforce. Tem controllers, models, scripts, forms, templates, JS e SCSS de cliente. Não se edita.
modules / server
Um cartridge à parte (modules) com o módulo server, que faz o roteamento no estilo Express. Tudo em modules pode ser carregado com require('nome'), sem caminho, e o cartridge não precisa estar no cartridge path.
Cartridge stack
A pilha de cartridges no cartridge path: custom → LINK → plugin → base, da esquerda para a direita.
Controller
Arquivo em cartridge/controllers/ que registra rotas (Product-Show = arquivo Product.js, rota Show).
Model (ViewModel)
Converte objetos da Script API (que às vezes se comportam como objetos Java) em objetos JavaScript puros e serializáveis, prontos para o template ou para JSON.
Decorator
Função que acrescenta propriedades a um model (models/product/decorators/price.js etc.). Também é o nome do template-moldura ISML (<isdecorate>), que é outro conceito.
Factory
Escolhe e monta o model certo para um caso (ex.: scripts/factories/product.js para full product, tile, set, bundle).
Middleware
Função (req, res, next) encadeada numa rota: https, cache, CSRF, login obrigatório, consent.
sgmf-scripts
Ferramentas de linha de comando do SFRA: compilam JS e SCSS (webpack), fazem lint e upload e criam cartridges.

O SFRA usa uma variação de MVC: o controller recebe o request e orquestra; o model busca dados pela Script API e os converte em JSON; a view é o ISML (ou a resposta JSON, nas rotas AJAX).

Como uma página é gerada

A documentação descreve o caminho de execução de um controller assim:

  1. A URL termina em Controller-Rota (ex.: Product-Show). A plataforma procura controllers/Product.js no cartridge path, da esquerda para a direita. Se não achar controller, procura um pipeline com o mesmo nome.
  2. O arquivo é carregado: os require do topo rodam (incluindo require('server')).
  3. module.exports = server.exports() registra todas as rotas criadas com server.get, server.post e server.use, e o servidor executa a que corresponde a Show.
  4. A cadeia de middleware roda em ordem; cada passo chama next().
  5. Ao final, o evento route:BeforeComplete dispara (é onde os forms gravam dados) e depois route:Complete, quando o server renderiza o ISML (res.render) ou o JSON (res.json) com o viewData acumulado.

Busca e listagem (PLP)

Busca por palavra-chave e navegação por categoria passam pelo mesmo controller, Search-Show, que usa o índice de busca via dw.catalog.ProductSearchModel, nunca consultas ao banco.

  • Refinements (filtros) vêm das refinement definitions da categoria (herdadas da raiz) e aparecem na barra lateral via Search-Refinebar (cacheada).
  • Sorting: opções de ordenação do BM (CatalogMgr.getSortingOptions()) e a regra padrão da categoria.
  • Paginação e "mais resultados": Search-UpdateGrid devolve só a grade.
  • Tiles: cada produto na grade é um remote include de Tile-Show (cacheado), uma das peças de performance do SFRA.
  • Search suggestions (autocomplete): SearchServices-GetSuggestions.
  • Conteúdo: a aba de artigos usa Search-Content com ContentSearchModel.

Configuração de busca (searchable attributes, sinônimos, search redirects, refinements, sorting rules) é feita no BM (Merchant Tools > Search). Depois de mudar atributos pesquisáveis ou refinements, o índice precisa ser reconstruído. Código customizado só entra quando a necessidade não é atendida por configuração.

O checkout é uma página única com estágios (shipping, payment, placeOrder) controlados no cliente; cada submissão é um POST AJAX que devolve JSON com o model atualizado (ou com fieldErrors e serverErrors).

JavaScript e SCSS de cliente

O JS de cliente usa CommonJS (require), jQuery e Bootstrap, e é empacotado pelo webpack via sgmf-scripts. As regras de descoberta do sgmf-scripts (em lib/helpers.js) são:

  • JS: cada arquivo client/<locale>/js/*.js (só o primeiro nível) é um entry point e vira static/<locale>/js/<nome>.js. Subpastas (product/, components/) são módulos importados.
  • SCSS: todo .scss em client/<locale>/scss/** que não começa com _ vira static/<locale>/css/…/<nome>.css. Parciais (_variables.scss) só são importados.
  • Aliases: o package.json do seu cartridge declara "paths": { "base": "../storefront-reference-architecture/cartridges/app_storefront_base/" }, e então require('base/product/detail') ou @import "~base/variables" apontam para o base.

Estendendo o JS de cliente num cartridge próprio

O static/default/js/productDetail.js do seu cartridge é um bundle completo que substitui o do base (o cartridge path resolve /js/productDetail.js para o seu). Por isso o seu entry point reimporta tudo o que a página precisa. Sem o entry point no seu cartridge, a alteração não entra em vigor.

O que muda quando o SFRA ou a plataforma é atualizado

Atualizações do SFRA

O SFRA segue versionamento semântico (vMAJOR.MINOR.PATCH): major quebra compatibilidade, minor traz features compatíveis, patch traz correções. Todos os repositórios (base, plugins, storefrontdata) recebem tags iguais, e só as versões marcadas como release no GitHub foram testadas em conjunto com os plugins. A documentação recomenda fazer checkout da mesma tag em todos os repositórios.

ElementoImpacto típico de um upgradeComo reduzir o atrito
ControllersRotas novas ou ajustadas; middlewares diferentesEstenda com append/prepend em vez de replace; você herda as mudanças.
ModelsPropriedades novas (as existentes mantêm a estrutura entre minors)Use module.superModule e acrescente propriedades.
TemplatesO base muda HTML e classes; a sua cópia sobrescrita não mudaSobrescreva o menor template possível (um componente, não a página).
JS e SCSS de clienteMódulos e eventos mudamEstenda módulos com require('base/…'); recompile sempre.
Dependências npmVersões de webpack, sass e sgmf mudamRode npm install a cada versão nova (a documentação exige).
Dados de demostorefrontdata muda juntoUse a mesma tag.

O procedimento de upgrade em si: substitua os diretórios do base e dos plugins pela tag nova, rode npm install, recompile, rode lint e testes, compare as sobrescritas de templates com as versões novas do base, suba numa sandbox e teste os fluxos críticos.

Atualizações da plataforma B2C Commerce

  • As releases chegam primeiro às sandboxes (preview) e depois ao PIG (veja a tabela de instâncias no tema 01). Leia as release notes e teste nas sandboxes.
  • A Script API evolui com compatibility modes: comportamentos que quebram compatibilidade só valem quando a code version passa para o modo novo. Você decide quando subir o modo e testa antes.
  • APIs são depreciadas antes de removidas; o log de deprecação e a documentação apontam o que trocar.
  • Configurações de BM novas (feature switches) podem chegar desligadas.

Um projeto que nunca editou o app_storefront_base faz o upgrade trocando uma pasta e reexecutando o build. Cada linha alterada no base vira um merge manual no próximo upgrade. Essa é a razão prática da regra "não edite o base".

Anti-padrões e pegadinhas de prova

Editar app_storefront_base ou modules/server. Anula a garantia de compatibilidade e transforma cada upgrade em merge manual.

Copiar o controller inteiro do base para o custom. Você deixa de receber correções. Use server.extend(module.superModule) com append/prepend (tema 06).

Editar arquivos em static/default/js. São gerados; o próximo build sobrescreve. Edite client/ e recompile.

Consultar o banco para montar a PLP. A listagem usa o índice (ProductSearchModel), que é rápido e respeita refinements, sorting e promoções.

  • "Ordem de resolução do cartridge path" → esquerda para a direita, o primeiro vence.
  • "O que o model faz no SFRA?" → converte objetos da Script API em JSON serializável para template ou AJAX.
  • "Como requerer o módulo server?" → require('server'), sem caminho, porque está em modules.
  • "Qual evento grava dados de forms antes da renderização?" → route:BeforeComplete.
  • "Qual arquivo SCSS não gera CSS?" → os que começam com _ (parciais).
  • "Bootstrap de qual versão?" → a documentação atual de compliance cita Bootstrap 5 (versões antigas do SFRA usavam Bootstrap 4).

  • Nomear as camadas da pilha (custom, LINK, plugin, base) e a regra de resolução do cartridge path.
  • Descrever as pastas do base: controllers, models, scripts (middleware, helpers, factories), forms, templates, client, static, experience.
  • Relacionar cada page type a controller, rota e template.
  • Explicar a execução de um controller: server.exports(), middleware, route:BeforeComplete e route:Complete.
  • Saber como o page.isml decora as páginas e como os assets são adicionados.
  • Descrever Search-Show, refinements, sorting, tiles e o uso do índice.
  • Explicar o build de JS e SCSS (entry points, parciais, aliases base/).
  • Avaliar o impacto de upgrades do SFRA (semver, tags) e da plataforma (releases, compatibility mode).

    1. O do app_storefront_base
    2. O do app_custom

    4. Todos são mesclados

  2. Qual afirmação sobre os models do SFRA é verdadeira?

    1. São objetos da Script API passados direto ao template
    2. Convertem objetos da Script API em objetos JavaScript puros e serializáveis
    3. Ficam no cartridge modules
    4. São gerados pelo webpack
    ver resposta

    b. A documentação define o ViewModel como um objeto JS serializável que combina dados de vários objetos da Script API.

  3. Você criou client/default/scss/_brand.scss e client/default/scss/brand.scss. O que o build gera?

    1. Os dois CSS
    2. Só static/default/css/brand.css
    3. Nenhum
    4. Só _brand.css
    ver resposta

    b. O sgmf-scripts ignora arquivos que começam com _; eles são parciais importados por outros.

  4. Por que a Salesforce recomenda não modificar o app_storefront_base?

    1. O arquivo é somente leitura no servidor
    2. Para manter a compatibilidade garantida entre releases e facilitar upgrades e correções
    3. Porque o base não pode ser enviado por WebDAV
    4. Porque o base roda em outro motor de script
    ver resposta

    b. Editar o base ou o módulo server anula a garantia de compatibilidade e transforma upgrades em merges manuais.

  5. Onde o SFRA busca os produtos de uma PLP?

    1. ProductMgr.queryAllSiteProducts()
    2. No índice de busca, via ProductSearchModel
    3. Num custom object
    4. Na OCAPI
    ver resposta

    b. Search-Show usa ProductSearchModel sobre o índice. queryAllSiteProducts é para jobs.

  6. Num upgrade do SFRA de v6.1.0 para v6.3.0, o que a semver garante?

    1. Nada
    2. Features novas compatíveis com a major 6
    3. Quebra de compatibilidade
    4. Só correções de segurança
    ver resposta

    b. Minor = funcionalidade nova compatível dentro da major. Mesmo assim, templates sobrescritos precisam de revisão manual.

  7. Você precisa injetar um script de analytics em todas as páginas sem sobrescrever o page.isml. O que usar?

    1. Editar o page.isml do base
    2. Registrar o hook app.template.afterFooter (ou beforeHeader) num cartridge próprio
    3. Usar OnRequest
    4. Um job
    ver resposta

    b. O page.isml chama esses hooks justamente para extensões. Lembre que eles rodam em páginas cacheadas.
