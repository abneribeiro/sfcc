Performance e escalabilidade

No B2C Commerce, performance depende de três coisas: servir o máximo possível do cache (page cache no web tier e custom caches no app server), usar o índice de busca em vez de percorrer o banco, e respeitar as quotas que a plataforma impõe para proteger o ambiente compartilhado. Este tema mostra como configurar cada uma e como reconhecer o código que destrói a escalabilidade.

Conceitos e glossário

Page cache
Cache de HTML no web adapter (camada web). Num cache hit, o controller e os templates nem executam. A chave é a URL completa, mais o contexto de preço e promoção quando a página é personalizada.
Static cache
Cache de imagens, CSS e JS. Em produção, o TTL mínimo é 24 h.
Remote include
<isinclude url="…"/>: um fragmento buscado pelo web adapter numa requisição separada, com cache próprio. É assim que se misturam partes estáticas e dinâmicas na mesma página.
Local include
<isinclude template="…"/>: renderizado no mesmo processamento e no mesmo cache da página, que fica com a menor duração entre os templates incluídos.
Custom cache
Cache em memória do app server (dw.system.CacheMgr), definido em caches.json, para dados caros de calcular.
Quota
Limite imposto pela plataforma a APIs, objetos e tamanhos. Quotas enforced geram exceção; as outras geram aviso no log de quota.

Page cache: iscache × middleware do SFRA

Existem duas formas de marcar uma resposta como cacheável. Em SFRA, prefira o middleware na rota, que concentra a política de cache no controller:

Rota do SFRA baseMiddleware
Home-Show, Default-Start, Search-Refinebar, Search-Content, Page-Show, Stores-Find, SearchServices-GetSuggestionsapplyDefaultCache
Product-Show, Product-ShowQuickView, Tile-ShowapplyPromotionSensitiveCache
Search-Show, Search-ShowAjaxapplyShortPromotionSensitiveCache
Cart-*, Checkout-*, Account-*sem cache (dados do comprador)

O equivalente em ISML

  • É obrigatório informar type ou varyby.
  • varyby="price_promotion" guarda variações por promoções ativas, regras de ordenação, price books aplicáveis e grupos de A/B test. Use só se a página realmente varia por esses fatores, porque fragmenta o cache. Personalização por outros critérios (nome, segmento custom) não pode ir para o cache.
  • Se um template ou um include local tiver varyby, a página inteira é tratada como personalizada. A duração efetiva é a menor entre os includes locais.
  • O page cache precisa estar habilitado no site (Administration > Sites > Manage Sites > site > Cache). Sem isso, iscache é ignorado. Em produção ele não pode ser desligado.

Remote includes: separar o dinâmico do estático

  • Página cacheada + fragmento por comprador (minicart, saudação, wishlist) = remote include sem cache. Assim, 99% do HTML sai do cache.
  • Checklist oficial: no máximo 20 remote includes por página e profundidade de 3 a 7 (quanto menor, melhor). Cada <isslot> usa 2 remote includes internamente.
  • Os parâmetros do remote include fazem parte da chave. Não use parâmetros únicos (ID do cliente, timestamp) em fragmentos cacheáveis.
  • Não use remote include com parâmetros únicos para montar tiles de busca.

Hit ratio, URL diversity e invalidação

  • Meta: hit ratio de pelo menos 70% por controller, e acima de 90% é melhor. Acompanhe na aba técnica de Reports & Dashboards.
  • URL diversity derruba o hit ratio. Mantenha parâmetros em ordem alfabética e sem nomes vazios, remova parâmetros únicos (dados do comprador vão em sessão ou cookie), encurte as URLs e não ponha IDs de cliente em links de e-mail marketing. Para parâmetros de campanha inevitáveis, use a feature switch Web Adapter Cache Key Ignore by Query String.
  • GET × POST: POST sempre ignora o page cache. Formulários de busca e filtro devem usar GET.
  • Invalidação: acontece por replicação ou por invalidação explícita no BM (o site inteiro ou uma partição), de forma gradual em cerca de 15 minutos. Partições: até 10, com até 20 pipelines ou controllers cada, sendo cada controller em só uma partição. Remote includes não são invalidados junto com a página que os contém, por isso coloque-os numa partição separada.
  • Invalidar o cache em produção causa pico de carga no app server. Evite fazer isso no horário de pico.

Custom caches (CacheMgr)

Para dados caros de calcular, ou respostas de serviços que mudam pouco, que você lê em muitas requisições:

  • Cerca de 20 MB por app server para todos os caches; até 100 caches por code version; entradas de até 128 KB; IDs únicos entre cartridges (ID duplicado desabilita o cache e gera log de erro).
  • Guardam só primitivos e objetos em árvore (JSON-like), nunca objetos da Script API como Product ou Basket. O que volta do cache é uma cópia imutável.
  • Não são compartilhados entre app servers, e invalidate(key) só limpa o servidor atual. Não há garantia de persistência: o loader precisa sempre conseguir recalcular.
  • São limpos quando a code version muda ou é ativada, e ao fim de replicações de código ou de dados.

Código do lado do servidor e front-end

  • onRequest/onSession rodam em toda requisição ou sessão. Mantenha-os com menos de ~10 ms e sem chamadas externas.
  • Sem chamadas a terceiros em Home, PLP, PDP e tiles. Quando forem inevitáveis, use timeout baixo (~1 s), porque uma thread esperando não atende ninguém.
  • Paginação: até 24 produtos por página de listagem (checklist) e um teto como 120 em "ver todos". Escopo controlado no "Sort All".
  • Não reserve a cesta várias vezes, nem reserve e crie o pedido na mesma requisição.
  • Sem objetos desnecessários: wishlist para todo anônimo, atributos de sessão, cookies e custom objects sem job de limpeza.
  • Controllers não chamam outros controllers. Reutilize helpers.
  • Sintaxe: o checklist oficial de eficiência recomenda var em vez de let/const no script de servidor, por limitações do motor Rhino com escopo de bloco.
  • Front-end: scripts no fim do body ou com defer, CSS e JS minificados (o build do SFRA já faz isso), imagens no tamanho certo (Dynamic Imaging Service com getImageURL({scaleWidth: …})), SVG para ícones, menos domínios e menos redirects, CDN.
  • Jobs: job load factor (segundos de job por dia ÷ 86.400) abaixo de 0,20 em Staging e Production.

A recomendação sobre var vem do Knowledge Article 000391851 (2026). O motor atual aceita boa parte da sintaxe ES6 conforme o modo de compatibilidade do site. Siga o padrão do projeto, mas saiba que é isso que a documentação recomenda.

Anti-padrões e pegadinhas de prova

Cachear página com dado do comprador (nome, cesta, endereço): outros compradores veem os dados errados, e há vazamento de PII. Isole em remote include sem cache.

Percorrer variantes em cada tile da PLP: milhares de objetos tocados por render e risco de quota. Use os hits do índice.

varyby="price_promotion" em todas as páginas "por precaução": fragmenta o cache sem necessidade.

Guardar Product ou Basket em custom cache ou sessão. Só dados serializáveis e pequenos.

  • Remote include tem cache próprio; local include herda e reduz o cache da página.
  • iscache status="off" é deprecated: omita o elemento ou use if.
  • Em SFRA, cache por middleware: cache.applyDefaultCache e similares.
  • Custom cache: caches.json referenciado no package.json; CacheMgr.getCache(id).get(key, loader).
  • Listagens: ProductSearchModel e os hits, não Category.getProducts().

Checklist: você precisa saber

  • Configurar o page cache por middleware (SFRA) ou iscache, com ou sem personalização.
  • Usar remote includes para partes por comprador, dentro dos limites de quantidade e profundidade.
  • Aumentar o hit ratio (URL diversity, GET) e invalidar por partição.
  • Criar e usar custom caches respeitando os limites e a natureza local por app server.
  • Trocar APIs de banco por APIs do índice de busca em listagens.
  • Reconhecer e evitar violações de quota; dimensionar transações; mover o pesado para jobs.

Questões de fixação

  1. A PDP é cacheada por 24 h, mas a disponibilidade deve atualizar a cada 30 minutos. Como resolver?

    1. Reduzir o cache da PDP inteira para 30 min
    2. Renderizar a disponibilidade num remote include com applyInventorySensitiveCache
    3. Desligar o cache
    4. Usar varyby
    ver resposta

    b. O remote include tem cache próprio; um local include reduziria o cache da página inteira.

  2. Qual a forma recomendada de não cachear um template?

    1. <iscache status="off"/>
    2. Omitir o iscache (ou usar o atributo if)
    3. hour="0"
    4. varyby="none"
    ver resposta

    b. status="off" é deprecated e impede reativar o cache.

  3. Uma página varia por price book do grupo de clientes. O que configurar?

    1. Sem cache
    2. Cache personalizado: varyby="price_promotion" ou applyPromotionSensitiveCache
    3. Custom cache
    4. Remote include por cliente
    ver resposta

    b.

  4. Um custom cache é invalidado com cache.invalidate(key), mas alguns compradores ainda veem o valor antigo. Por quê?

    1. Bug da plataforma
    2. Custom caches são locais a cada app server; a invalidação só limpa o servidor atual
    3. Falta reindexar
    4. O TTL é infinito
    ver resposta

    b. Use TTL curto para dados que mudam.

  5. Os tiles da PLP chamam product.getVariants() para mostrar as cores. O que trocar?

    1. Nada
    2. ProductSearchHit.getRepresentedVariationValues('color')
    3. Um custom object com as cores
    4. OCAPI
    ver resposta

    b. É uma API "index-friendly" da lista oficial.

  6. Por que um formulário de filtro deveria usar GET?

    1. Segurança
    2. POST sempre ignora o page cache
    3. GET é mais curto
    4. Exigência do CSRF
    ver resposta

    b. (Formulários que alteram estado continuam POST com CSRF.)
