IDE, WebDAV e deploy de código

No B2C Commerce, o código é escrito localmente mas roda no servidor: cada alteração precisa chegar a uma code version da sua sandbox para ser testada. Este tema monta o ambiente de trabalho completo: a IDE e as suas extensões, as credenciais certas, o WebDAV, os modos de enviar código (sob demanda e contínuo), o CLI oficial, o debugger de scripts no servidor e a leitura de logs sem sair do editor.

Conceitos e glossário

WebDAV
Protocolo HTTP de arquivos que a instância expõe em /on/demandware.servlet/webdav/Sites/…: cartridges (code versions), logs, IMPEX, catálogos e libraries.
Code sync / watch
Envio automático de cada arquivo salvo para a code version da sandbox.
dw.json
Arquivo de conexão do projeto (host, usuário, access key, code version, client ID e secret), lido pelas ferramentas.
Access key
Credencial gerada no BM por usuário e por escopo (WebDAV File Access and UX Studio, OCAPI, storefront protegido) que substitui a senha do Account Manager em ferramentas externas. Validade de um ano.
Script debugger
Depurador de scripts que rodam no servidor (controllers, hooks, jobs, custom APIs), com breakpoints e inspeção de variáveis.
DAP
Debug Adapter Protocol: o padrão que permite a qualquer IDE compatível conversar com um depurador (o b2c debug implementa um adaptador).

A extensão oficial é publicada como Salesforce.b2c-vs-extension no Visual Studio Marketplace e no Open VSX, segundo a documentação do B2C Developer Tooling. As ferramentas da comunidade (Prophet, plugins JetBrains) mudam de mantenedor e de recursos com o tempo; confira o estado atual antes de padronizá-las no time. Para a prova, o conceito importa: uma IDE conectada por WebDAV, que envia cartridges para uma code version e depura no servidor.

Instalação e configuração

  1. Instale a extensão (Marketplace ou Open VSX) e o Node.js (para o build do SFRA e o CLI).
  2. No BM da sandbox, gere uma access key com escopo WebDAV File Access and UX Studio (seu usuário > Manage Access Keys).
  3. Para operações de code version e sandboxes, crie um API client no Account Manager (client ID e secret) com as permissões necessárias.
  4. Crie o dw.json na raiz do projeto e adicione-o ao .gitignore.
  5. Abra o projeto: a extensão detecta os cartridges (pastas com .project e cartridge/) e a instância ativa aparece na barra de status.

IntelliSense da Script API em outras IDEs

Com a extensão oficial, isso é automático e não escreve nada no repositório. Para o código require('server') do SFRA, a extensão também injeta tipos do módulo server quando encontra o cartridge modules.

Use uma code version por desenvolvedor na sandbox compartilhada (ex.: dev_ana), ou uma sandbox por desenvolvedor. A documentação de boas práticas recomenda nomes únicos para não sobrescrever o trabalho de colegas.

WebDAV na prática

PastaConteúdo
/Sites/Cartridges/<code-version>/Os cartridges de cada code version (o arquivo .version indica a ativa)
/Sites/Logs/Logs do sistema e custom; subpastas como deprecation/ e logs de jobs
/Sites/Impex/Área de import/export: src/ (entrada), arquivos gerados por exports e jobs
/Sites/Catalogs/<catálogo>/, /Sites/Libraries/<library>/Estáticos de catálogo e de conteúdo (imagens)
/Sites/Dynamic/<site>/Arquivos dinâmicos do site

Os caminhos de WebDAV de cada instância aparecem em Administration > Site Development > Development Setup. As permissões de escrita por pasta vêm da role do usuário (aba WebDAV Permissions). Qualquer cliente WebDAV (a extensão, Cyberduck, WinSCP) funciona com usuário e access key.

A plataforma limita o nome da pasta de cartridges a 50 caracteres no WebDAV e recomenda no máximo 100 mil arquivos por pasta.

Enviando código

No dia a dia (sandbox)

Na extensão, o code sync faz o papel do watch, e o comando de deploy envia sob demanda. Lembre de recompilar o JS e o SCSS de cliente antes: o watch envia o que está em static/, não o fonte de client/.

b2c CLI × sfcc-ci

O sfcc-ci foi depreciado; o substituto oficial é o @salesforce/b2c-cli. Mapeamento dos comandos mais comuns:

sfcc-ci (legado)b2c CLI
sfcc-ci client:auth <id> <secret>b2c auth client --client-id … --client-secret … (ou variáveis SFCC_CLIENT_ID/SFCC_CLIENT_SECRET)
sfcc-ci code:deployb2c code deploy (a partir do fonte local)
sfcc-ci code:activate <v>b2c code activate <v>
sfcc-ci code:listb2c code list
sfcc-ci instance:upload <arquivo>b2c webdav put …
sfcc-ci instance:import <zip>b2c job import … / b2c content import …
sfcc-ci sandbox:createb2c sandbox create

Para Staging e Production

  • Staging: upload numa code version nova (ex.: rel_2026_11_04), com o certificado de cliente exigido para uploads em Staging (2FA). Normalmente feito pelo pipeline de CI (tema 16).
  • Teste em Staging e replique para Development; depois code replication para Production (tema 01).
  • Production: uploads bloqueados (configuração obrigatória); o código chega só por replicação.

Script debugger

O debugger para em qualquer código do servidor: controllers SFRA, hooks (inclusive de OCAPI/SCAPI), jobs, custom APIs, helpers.

Requisitos

  • Credencial Basic: usuário do BM + access key com escopo WebDAV File Access and UX Studio. OAuth não serve, e a senha do Account Manager não é aceita com login unificado.
  • Usuário com a permissão de WebDAV de customização (WebDAV_Manage_Customization).
  • Os cartridges locais iguais aos da code version ativa (para mapear linhas).

Depurando no VS Code

  1. Inicie uma sessão do B2C Script Debugger pela extensão.
  2. Ponha breakpoints (ou log points, que registram sem parar) no arquivo do cartridge.
  3. Dispare o código: abra a página, chame a rota por AJAX ou rode o job.
  4. Inspecione variáveis e a pilha, avalie expressões, avance passo a passo e solte (resume).

Breakpoints pausam requests e jobs de verdade, e avaliar expressões pode alterar estado. Depure em sandbox. Numa instância com vários application servers, o request precisa cair no mesmo app server da sessão do debugger: envie o cookie dwsid da sessão (a extensão tem o comando Copy Debugger Session ID). Sandboxes têm um único app server e não precisam disso.

Logs sem sair do editor

A extensão tem Start/Stop Tailing Logs, que transmite error-*, warn-*, info-* e os logs custom (custom-*) para o painel de saída. Tipos de log, categorias e Log Center estão no tema 21.

Qualidade no editor

  • ESLint com a configuração do SFRA (o projeto base traz npm run lint), que pega erros antes do upload.
  • Stylelint para SCSS (scripts lint:css criados pelo sgmf-scripts).
  • isml-linter (comunidade) para templates ISML: tags malformadas, isset sem escopo, encoding.
  • Scaffolding da extensão: cartridges, controllers, hooks e jobs a partir de modelos.
  • Testes unitários locais (mocha + proxyquire) rodando sem servidor (tema 16).

Anti-padrões e pegadinhas de prova

dw.json com credenciais no Git. Use .gitignore; no CI, variáveis de ambiente.

Vários devs na mesma code version da sandbox compartilhada: um sobrescreve o outro.

Editar arquivos direto pelo WebDAV no servidor (sem passar pelo Git): a mudança se perde no próximo deploy e ninguém sabe que existiu.

  • Código chega à instância via WebDAV, numa code version; precisa estar ativa para valer.
  • Credencial de WebDAV com login unificado: access key, não a senha do Account Manager.
  • Production: upload bloqueado; Staging: upload com certificado de cliente; Production recebe por replicação.
  • O dw.json define host, credenciais e code version de destino.
  • sfcc-ci está depreciado; o substituto é o b2c CLI.

Checklist: você precisa saber

  • Instalar e configurar a IDE (extensão oficial ou alternativa) com dw.json e access key.
  • Explicar o WebDAV e as suas pastas (Cartridges, Logs, Impex, Catalogs, Libraries).
  • Enviar código com watch e deploy (b2c CLI e scripts do SFRA) e ativar code versions.
  • Saber as regras de upload em Staging (certificado) e Production (bloqueado).
  • Depurar scripts no servidor (requisitos, fluxo, cuidados).
  • Ler logs pela IDE ou pelo CLI.
  • Configurar lint e IntelliSense.
