Controllers JavaScript

Controllers são os scripts do servidor que recebem cada request do storefront, orquestram a lógica (models, helpers, serviços) e produzem a resposta: HTML, JSON, XML, redirect ou uma página do Page Designer. Este tema detalha o módulo server do SFRA por dentro: como as rotas são registradas e executadas, o que existe em req e res, cada middleware do base, os eventos de rota, os remote includes, o tratamento de erros e os padrões para escrever controllers novos e modificar os existentes.

Conceitos e glossário

Pela documentação: controllers ficam na pasta controllers/ no topo do cartridge, têm extensão .js (ou .ds), seguem CommonJS, e os métodos exportados precisam ser públicos para atender requests. No SFRA, server.exports() marca as rotas como públicas.

Rota
Um nome (Show) associado a uma cadeia de funções. A URL Product-Show = controller Product.js + rota Show.
Middleware
Cada função (req, res, next) da cadeia. Chama next() para seguir ou next(new Error(…)) para abortar.
req
Objeto do SFRA que embrulha request, customer e session globais (querystring, form, currentCustomer, locale, session…). É congelado (Object.freeze) quando a rota começa.
res
Objeto do SFRA para montar a resposta: render, json, xml, page, redirect, setViewData, setStatusCode, cache…
viewData
Objeto acumulado ao longo da cadeia que vira o pdict do ISML ou o corpo do JSON.
Remote include
Um request separado (com cache próprio) que o Web Adapter junta à página. Rotas desse tipo usam server.middleware.include.

O primeiro controller

Como a documentação descreve a execução: a plataforma acha o primeiro Hello.js no cartridge path; os require do topo rodam; server.exports() registra as rotas; o servidor executa a rota cujo nome bate com a URL.

A documentação recomenda carregar módulos só quando precisa ("Only require modules when you need them"). Por isso o SFRA faz require de dw/… dentro da função da rota: um controller com dez rotas não paga o custo dos módulos que só uma delas usa.

Como uma rota é executada por dentro

O código do modules/server/route.js mostra a ordem exata:

  • server.get e server.post inserem middleware.get/post no início da cadeia; server.use não filtra método.
  • Registrar duas rotas com o mesmo nome no mesmo server lança Route with this name already exists.
  • res.render() não renderiza na hora: registra a intenção. A renderização acontece em route:Complete, com o viewData final. Por isso os append de outros cartridges ainda podem alterar os dados.
  • Se mais de um render/json for chamado, vale o último (appendRenderings substitui a renderização anterior).
  • Um res.redirect() interrompe a cadeia no próximo next().
  • next(new Error('…')) loga a mensagem e lança o erro; a plataforma chama o controller de erro (Error-Start).

A documentação desencoraja usar os globais (request, session, customer) diretamente nos controllers SFRA; prefira req e res.

Uma rota protegida completa

Ordem importa: filtros de acesso (https, validateLoggedIn, validateRequest) vêm antes da função principal. Cache vem cedo, porque só define propriedades que o server aplica no fim. Rotas com dados do comprador não recebem cache de página.

Escrevendo o seu middleware

Eventos de rota e viewData

A documentação lista os eventos emitidos pelo server; todos recebem req e res:

EventoQuandoUso típico
route:StartAntes da cadeiaInstrumentação
route:StepAntes de cada passoDepuração
route:RedirectAntes de um redirectLimpeza, logs
route:BeforeCompleteDepois de todos os passos, antes da renderizaçãoGravar dados de forms no banco, depois que todos os appends já validaram
route:CompletePor últimoO server o usa para aplicar cache e renderizar

O padrão do SFRA para gravar dados (ex.: Account-SaveProfile) é este: o passo principal valida o form e põe o resultado no viewData; a escrita no banco fica num listener de route:BeforeComplete. Assim, um append de outro cartridge pode acrescentar validações e marcar erro antes de qualquer coisa ser gravada.

Dentro de um passo, this é o objeto Route, que é um EventEmitter; daí o this.on(…). O hook app.server.registerRoute (chamado pelo server.js a cada rota registrada) permite assinar eventos de todas as rotas a partir de um cartridge.

Remote includes e fragmentos

Um remote include é uma rota que devolve um pedaço de HTML, chamado pelo Web Adapter como request separado e cacheado à parte. O SFRA usa remote includes no header de conta (Account-Header), no minicart (Cart-MiniCart), no consentimento (ConsentTracking-Check) e nos tiles da PLP (Tile-Show).

Remote include × local include: <isinclude template="…"/> renderiza outro template dentro do mesmo request (mesmo cache, mesmo pdict); <isinclude url="…"/> chama outra rota (request novo, cache próprio, sem acesso ao pdict da página). O ISML está no tema 10; a performance, no tema 20.

Erros e controllers de sistema

A plataforma chama controllers com nomes reservados em situações especiais. Os do SFRA:

Controller-RotaQuandoO que o SFRA faz
Default-StartAcesso à raiz do siteRenderiza a home (página homepage do Page Designer, se visível)
Default-OfflineSite offlineTemplate siteOffline
Error-StartExceção não tratadaStatus 500; JSON para AJAX ou o template error; detalhes só fora de Production e Staging
Error-ErrorCodeErros com código (ex.: checkout)Mensagem message.error.<código>
Home-ErrorNotFoundPágina não encontradaStatus 404 e error/notFound
CSRF-Fail / CSRF-AjaxFailToken CSRF inválidoPágina ou JSON de erro

A documentação de controllers ainda observa que erros de JavaScript vão para os logs customerror_*; que, por padrão, a plataforma devolve 410 em erros não tratados (404 também serve, desde que o template não use <isslot>, <iscomponent> nem <isinclude>); e que, para tratar explicitamente, use try/catch.

A documentação desaconselha controllers chamando outros controllers (risco de dependência circular; aceitável só em casos como chamadas não públicas do checkout) e chamadas a pipelets ou pipelines a partir de controllers. Extraia a lógica comum para um helper em scripts/.

Anti-padrões e pegadinhas de prova

Esquecer next(). A cadeia para e nada é renderizado (página em branco). Toda função da cadeia precisa chamar next() (ou emitir route:Complete deliberadamente).

Lógica de negócio pesada no controller. Controllers orquestram; regras ficam em helpers, models e serviços, que são testáveis e reutilizáveis por jobs e hooks.

Gravar no banco no passo principal de rotas que outros cartridges estendem. Use route:BeforeComplete.

Cache em rota com dados do comprador (nome, carrinho, preços personalizados sem personalized). Uma resposta pode ser servida a outra pessoa.

  • URL Cart-AddProduct → arquivo controllers/Cart.js, rota AddProduct.
  • "Só via remote include" → server.middleware.include.
  • "Exigir login" → userLoggedIn.validateLoggedIn (página) ou validateLoggedInAjax (AJAX).
  • "Proteger form de CSRF" → csrfProtection.generateToken na rota que renderiza e validateRequest/validateAjaxRequest na que recebe.
  • "Onde gravar dados do form para que extensões validem antes?" → route:BeforeComplete.
  • "Resposta JSON" → res.json(); "acrescentar dados" → res.setViewData().

Checklist: você precisa saber

  • Criar um controller com server.get/post e server.exports(), e mapear URL → arquivo e rota.
  • Explicar a execução da cadeia: freeze do req, steps, redirect, BeforeComplete, Complete, renderização tardia.
  • Usar req (querystring, form, body, currentCustomer, locale, session.privacyCache) e res (render, json, xml, page, redirect, viewData, status).
  • Aplicar os middlewares de filtro, cache, CSRF, login e consent na ordem certa.
  • Escrever middleware próprio e ouvir route:BeforeComplete.
  • Criar rotas de remote include e saber quando usá-las.
  • Conhecer Default-Start, Error-Start e Home-ErrorNotFound, e tratar erros com try/catch e logs.

Questões de fixação

  1. Qual URL executa a função registrada por server.get('Details', …) no arquivo controllers/Order.js?

    1. …/Order/Details
    2. …/Order-Details
    3. …/Details-Order
    4. …/order.details
    ver resposta

    b. O formato é Controller-Rota.

  2. Uma rota chama res.render('a', {x:1}) e depois um append chama res.setViewData({y:2}). O que o template recebe?

    1. Só x, porque o render já aconteceu
    2. x e y, porque a renderização ocorre só em route:Complete
    3. Só y
    4. Erro
    ver resposta

    b. render registra a intenção; o viewData final é renderizado depois de toda a cadeia.

  3. Qual middleware garante que uma rota só responda como remote include?

    1. server.middleware.https
    2. server.middleware.include
    3. cache.applyDefaultCache
    4. consentTracking.consent
    ver resposta

    b. Ele verifica req.includeRequest.

  4. Onde o SFRA recomenda gravar dados submetidos por um form, para que extensões possam validar antes?

    1. No primeiro passo da cadeia
    2. Num listener de route:BeforeComplete
    3. No template
    4. Em route:Start
    ver resposta

    b. A documentação descreve route:BeforeComplete como o evento usado para gravar dados de forms.

  5. Uma página de "Meus pedidos" usa cache.applyDefaultCache. Qual é o risco?

    1. Nenhum
    2. Servir a página de um comprador a outro, porque o conteúdo é pessoal e foi cacheado
    3. A página não carrega em HTTPS
    4. Erro de CSRF
    ver resposta

    b. Não cacheie conteúdo pessoal; se precisar de cache na página, mova a parte pessoal para um remote include sem cache.

  6. O que acontece se um passo da cadeia não chamar next() nem renderizar?

    1. A plataforma chama o próximo passo automaticamente
    2. A cadeia para e nada é renderizado
    3. Erro 500 imediato
    4. Redirect para a home
    ver resposta

    b. Sem next(), done() nunca roda e route:Complete nunca é emitido.

  7. Em Production, uma exceção não tratada num controller mostra o quê, no SFRA?

    1. O stack trace completo
    2. A página de erro genérica, sem detalhes (o Error-Start só mostra detalhes fora de Production e Staging)
    3. Página em branco
    4. Um JSON com o erro
    ver resposta

    b. O Error.js do base calcula showError pelo tipo de instância. O detalhe fica no customerror log.
